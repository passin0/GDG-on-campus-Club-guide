## 0. 什麼是專案？
>「專案（Project）是在獨特背景下，為了創造價值而發起的暫時性措施。」---PMBOK® Guide

看起來很神祕，我引用這句也是覺得這樣很深奧，但是就是三件事：
- 我要完成什麼
- 什麼時候要完成
- 我有多少資源可以用 

所以專案管理，簡單來說就是想辦法在這些限制下，把目標完成。假設你想認識專案管理，那先知道一下這些的差別。
- Project：為了完成一個目標而進行的暫時性工作。
- Program：把多個相關的 Project 組合起來管理。
- Product：Project 最後產生、並持續提供價值的東西。

### 0.1 軟體專案呢 ?
上次課程我們教學了 AI coding 工作流的
> 功能分析、系統設計、程式編寫、測試與維護

在傳統的軟體專案中大致上也是這樣，有個稱呼--瀑布式模型（Waterfall Model），把整個專案週期訂成一條順序階段，在個人開發就足夠使用了。

### 0.2 除了寫程式，我們還可以多做什麼 ?

在我認識的一些人裡面，剛開始想做專案的人可以分成兩種：
一種是我會(用 AI)寫 code 我想做東西，然後就開始讓 AI 寫程式開始迭代，做了一段時間後就開始模糊不太確定下一步要做什麼 ; 
一種是我想做但是我完全不知道從哪裡開始ㄚㄚㄚ(T_T)。

所以我會建議如果遇到以上問題的人可以先嘗試寫給自己一份專案規畫書，用來搞清楚「自己」究竟想做什麼。

同時，這份企劃也會是你用來跟夥伴、教授、客戶、評審交流的第一份重要資料。

#### 所以一個好的軟體專案企畫，可能需要哪些前提?
<details>
<summary>痛點分析</summary>

> 觀察你想解決的問題是什麼人群需要的，可以透過採訪、問卷、研究的形式，去收集各種資料，確認這個痛點是否需要被解決，而不是自己想像的。

如果你找不到問題，像是在黑客松或是提案競賽的時候。可以觀察你的目標客群（主題），從平常的流程開始。

例如：我在台北坐捷運，我每天要進站、拿出手機或是卡片、刷卡、收起來、排隊、找位置、出站也要一樣的流程。

展開流程你就可以總結出來，最大的痛點可能是進出站要操作很麻煩、或是臺灣人很遺憾地不能飛

> 當然，如果是你要開發解決自己問題的工具，也希望採訪一下自己，把自己的問題歸納成幾句話。 
</details>
<details>
<summary>問題定義 </summary>

> 將開頭觀察到的分散痛點，整理成一句具體且可被解決的「核心問題陳述」。

這句話要明確界定這次開發到底要處理的目標是什麼。接下來的所有規劃與迭代都可以回頭看看我們的核心問題。

>像是我們剛剛總結出，台灣人不能飛的痛點，那我們就要定義一個具體問題，本專案旨在解決台灣人不能飛而需要一個替代的大眾外掛工具才能起飛。
</details>
<details>
<summary>客群(使用者)分析</summary>
接著就要釐清這款產品「到底是要做給誰用的」，然後試著描繪出目標使用者的行為習慣、使用情境以及對技術的熟悉程度。
了解使用者是誰，才能設計出符合他們直覺與習慣的產品。

> 如果是你自己，也可以找朋友一起討論看看，你們如果有這類工具可以解決，你們希望怎麼解決。
</details>
<details>
<summary>使用具體情境</summary>

> 想一下一個實際的電影場景，使用者「在什麼時間、什麼地點、遇到了什麼狀況，進而開啟我們的系統，做什麼事」。

對內對外都可以更具體的知道我們需要什麼，模擬使用者從接觸產品到完成目標的全流程。
這能讓抽象的功能變得具體，更容易發現介面或流程設計上的缺失，也更好跟一些人解釋。
</details>
<details>
<summary>專案目標與範疇 </summary>

> 設定專案最終要達成的具體目標，並劃定這次開發的「邊界與不做的範圍」。

明確告訴大家「第一版（MVP）只做什麼」，防止我們突然想到，這裡可以加什麼那裏可以補充什麼，最後整個計畫超大做不完，時間亂掉。
控管時程與團隊資源是最重要的一部分，確保自己能準時的完成產品。
</details>

#### 說完了專案共有的前期藍圖，接著以下就是開始一個專案需要的軟體設計規畫了。
<details>
<summary>功能需求與非功能需求</summary>

> 功能需求，也就是我們解決前面的問題到底需要什麼功能。

例如要解決台灣人不能飛的問題，我們可能就需要蓋傳送門，這個傳送門應該需要有以下功能：
- 台語客語原住民語國語的語音辨識
- 可以傳送人、衣服、鹹酥雞、豆花
- 能長期承受臺灣阿嬤騎機車的撞擊

這樣把你設計需要的功能條列出來，再逐個撰寫細節，後面規劃會很清楚。

> 非功能設計，事實上也是很重要的，也就是沒辦法特別列成條件的

例如傳送要在十秒內、整個操作流程只要五秒不然別人會按喇叭、單次耗電不能超過[]度，這類的非功能也是我們可以寫下來的需求。
</details>
<details>
<summary>架構設計</summary>

在我們上一節課，我們有看到一個系統可以拆成多個功能，多個功能還可以拆成多個模組。而我們在規劃時就要完成這些部分。

> 規劃系統內部各模組之間如何分工與溝通，像是劃分前端、後端與資料庫的職責。

決定資料如何在系統中流動，以及 API 介面該如何對接。
好的架構能讓團隊成員平行分工，寫程式時才不會互相打架。
</details>
<details>
<summary>技術選用與理由 </summary>

> 根據專案需求、開發時程與團隊成員的熟悉度，選擇最合適的程式語言、框架與套件。

重點不在於用「最新、最炫」的技術，而是說明「為什麼這個技術最適合這個專案」。
合理的選型能大幅降低開發門檻，避免中途卡關或砍掉重練。

像是我開發的時候，第一個考量的就是組員比較熟悉，第二個考量就是社群量夠大(使用這個架構的人多)，因為我們很常需要查資料或是找錯誤，挑選網路上很多人討論得比較方便。

</details>
<details>
<summary>專案開發管理規劃 </summary>

> 規劃團隊要如何分工協作、排定開發時程以及管理任務進度（例如使用敏捷看板或 Git 版本控制）。

將大功能拆解成一週或兩週的小迭代，確保進度有在追蹤。
讓每個人都知道自己現在該做什麼、什麼時候要交出成果。
</details>
<details>
<summary>專案品質管理規劃</summary>

> 制定測試與審查機制，確保交出來的程式碼能正常運作且不易出錯。
包含自動化測試、同儕程式碼審查（Code Review）或是上線前的測試驗收。
在交付前把關品質，首先當然就是避免你出錯了才要查，而不是預先寫好，就像是數學需要驗算一樣，你可以把驗算算式先寫好，就可以更快的測試找到問題。此外就是如果你做出來的產品有穩定使用者的話，那就更需要做測試審查，像是線上遊戲的話，總不能你發布更新之後，然後阿不小心把段位計算寫反了結果都沒人發現，然後就被玩家抗議。
</details>
<details>
<summary>專案風險與限制 </summary>

> 預先盤點專案開發過程中可能遇到的瓶頸，例如：技術卡關、死線逼近、成員退選或外部 API 限制。

針對高風險項目提前思考替代方案或應變措施。

> 最重要的是，為專案預留足夠的時間空間去預備不知道項目但是可能會發生問題的風險。

知道限制在哪裡，專案才能在預算的資源與時間內安全落地。
</details>
<details>
<summary>預期成果or效益</summary>
說明專案完成後，能帶來什麼實質改變或價值（例如：節省 50% 作業時間、獲得 100 位活躍使用者）。
建立客觀的驗收標準或數據指標，用來評估這個專案是否算成功。
這能讓團隊與贊助者/評審清楚看到專案的最終影響力。
</details>
<details>
<summary>驗證與測試/MVP 測試</summary>

> 在寫出幾千行程式碼之前，我們要如何用最低成本驗證這個點子有人要？  

如果你是有目標要處理的，當然會需要在你把整個專案做完前，有一個樣品能試看看跟修正規劃，這就是 MVP 最小可行性產品（Minimum Viable Product）需要存在的目的，後面我們在細講怎麼規劃。

</details>

<small> note：自己開發的時候不一定需要全部都有，但是可以挑選記下你覺得當前最重要的項目。 </small>

### 0.3 現代正規專案開發的小補充
剛剛有提到傳統專案的瀑布式開發，那現代一些專案可能為了高速迭代或是同類競爭，就創造出更多模式，這些看看就好，不一定要學會，想成為 科技PM 的同學可以看一眼，然後去做更多搜尋。

1. 敏捷開發（Agile Development）
敏捷開發是一種核心思維。它將大型專案拆解為數個小週期，透過不斷的迭代（Iteration）來交付可運作的軟體。
- Scrum：目前最主流的敏捷框架。將工作固定在 1 至 4 週的衝刺（Sprint）中，每日透過每日站會（Daily Standup）對齊進度，並在衝刺結束時交付可交付的成果。補充指南 [2020 Scrum Guide](https://scrumguides.org/scrum-guide.html)

- 看板管理（Kanban）：核心在於視覺化工作流並限制在製品數量（WIP Limit），非常適合需求變動頻繁、需要彈性調整優先級的團隊。
2. 創新型開發模型
- 精實開發（Lean Development）：核心是「消除浪費」（如：過度的功能、多餘的等待）。它提倡「精實創業（Lean Startup）」精神，也就是 MVP 機制——用最快、最省資源的方式驗證市場。
- 螺旋模型（Spiral Model）：結合了瀑布模型與原型法（Prototyping）。其最大特色是加入強大的風險分析（Risk Analysis），每次迭代都沿著螺旋向外擴展，特別適合大型、高風險或國防醫療級的專案。
3. 現代維運一體化
- DevOps：將開發與維運融合。透過持續整合（CI）與持續部署（CD）的自動化工具鏈，讓軟體在幾分鐘內完成測試、打包並上線，實現「天天甚至每小時部署」的現代高頻率更新。

## 出發之前：想法哪裡來啊
如果是問我，我的想法大多不是專注在一個討論，或是坐下來仔細想想的時候。事實上大部分都源自於一些很突然的時候，上廁所的時候、吃飯的時候、期中考的時候、睡覺前的時候.....。

隨手記下一些零碎的想法在紙上或手機上是個不錯的方式。

馬上先來推薦文章，有點古老但是這是我找到比較貼近我想講的文章:
1. [IDEO 設計思維](https://designthinking.ideo.com/process?trk=article-ssr-frontend-pulse_little-text-block)
2. [Paul Graham：How to Get Startup Ideas](https://www.paulgraham.com/startupideas.html?utm_source=chatgpt.com)

> **不要「想出」Idea，要「注意到」Idea。**

好的想法常常不是坐在桌前：
 「我要想一個超棒的專案。」
硬想出來的。而是來自：

- 自己遇到的問題
- 某件事情很煩
- 某個流程很蠢
- 某個領域缺了一個東西
- 自己正在玩／研究某個東西，發現「為什麼沒有這個？」
- 進入一個新領域後，發現原本的人已經習慣了某些很奇怪的做法

>「做一個自己覺得很酷的東西」也是一個找 Idea 的方法之一。


---

### 你可以尋找的三種 Idea 來源
#### ① Problem-driven
> **「我遇到了什麼問題？」**
例如：

> 每次下載的檔案都亂七八糟 →  
> 做檔案整理 ai Agent

#### ② Interest-driven
> **「我對什麼東西感興趣？」**

例如：
> 我很喜歡音樂  
> ↓  
> 我一直想知道自己的手勢能不能指揮音樂  
> ↓  
> 手勢辨識 → 音樂控制

這甚至不需要一開始有「痛點」，就是：

> **「這東西感覺很酷，我想玩玩看。」**

#### ③ Domain-driven

> **「我進入一個我不熟悉的領域，看到了什麼奇怪的東西？」**

例如資工學生去：

- 社團
- 醫院
- 餐廳
- 行銷
- 運動
- 音樂
- 遊戲

然後突然：

> 「蛤？你們現在還在這樣做？為什麼？」

在我過去的感受最大的就是，**跨領域碰撞**很容易產生 Idea：懂程式的人進入另一個領域，很容易看到該領域原本沒被軟體解決的問題 ; 另一方面，法商人也可以在科技業發現更多還沒被解決的問題，或是帶自己學到的東西再次回到原本的領域。

我會說：
>到處跨領域是在找新的靈感，雖然我沒有什麼偉大的成就給同學們作範例，但是我覺得這是可以參考的一條有趣的路。

---

所以你可以把「找 Idea」變成一個**觀察任務**。例如：
> **這週記錄 5 件讓你覺得「很煩／很蠢／很好玩／很想改善／很好奇」的事情。**

完全不要求它們是好 Idea。

例如：

```text
今天：
1. 每次社課都有人不會用 Git 
2. Discord 裡資訊很容易被洗掉
3. 社團課的同學好像很常沒來(T_T)
4. 講師給的 MarkDown 文章很難整理
5. 要寫一篇文章還需要排版好麻煩
```

> **不要逼自己想出一個 Idea。先去生活、去玩、去學、去觀察，然後注意那些讓你「欸？」的東西。**

「欸？」可以是：
- **好煩** → Problem
- **好怪** → Opportunity
- **好酷** → Interest
- **為什麼沒有？** → Gap
- **如果可以這樣就好了** → Idea
- **我想試試看** → Project

> **Idea → Problem / Goal → MVP → Project Blueprint**

> **開始對世界產生「這東西是不是可以被做得不一樣？」的注意力。**

接下來，就可以出發了！

## 1. 產品跟提案的出發點：從痛點拆出真正的問題
提供那些在思考自己設計的專案是需要去公開上架、尋找使用者、競爭的人的起點。
### 1-1. 痛點 vs. 解答
痛點是使用者在現實中遇到的「阻礙、痛苦、浪費的時間」，而不是「缺少某個軟體或功能」。

> ❌ 錯誤痛點：「同學們沒有一個專屬的校園二手書交易平台。」（這是在強推解答）

> ⭕ 真實痛點：「大一新生買二手課本時，常常在 Line 群組被洗訊息，不知道誰手上有書，成交效率極低。」

### 1-2. 連續問五次「為什麼」（5 Whys 探究）

我們找到一個痛點後，像剝洋蔥一樣找出底層的原因。症狀：學生總是不來參加社團社課 (Q-Q)。

> Why 1？因為他們忘記時間。（表象原因）\
> Why 2？因為提醒訊息淹沒在社群裡。\
> Why 3？因為大家習慣把群組設靜音。\
> Why 4？因為群組裡太多無關的閒聊雜訊。\
> Why 5？因為公告和閒聊都丟在同一個群組，沒有分開。

根本問題：資訊缺乏「優先級分類」與「重要推播機制」。

### 1-3. 痛點的「頻率」與「強度」

不是所有的痛點都值得做成軟體專案，有些是真痛有些實際上是假痛。

好的專案問題通常具備「高頻率」或「高傷害（強度）」。大展評估矩陣之我懶得做圖片：

> 高頻 + 高強（例：每天選課/選餐卡爆）：黃金專案主題，一定要解決。

> 低頻 + 高強（例：一年一次的租屋合約糾紛）：值得解決，但需要考慮使用率。

> 高頻 + 低強（例：偶爾懶得手動輸入密碼）：可以解決，但可能不是剛需。

> 低頻 + 低強（例：一年用一次的校園地圖微調）：危險紅燈，做出來很可能沒人用。


### 1-4. 問題定義句型（Problem Statement Template）
用一句標準的公式，把散亂的痛點組合成一個「專案目標指南針」。
一個填空給你看看：

>「[哪一群特定使用者] 在 [什麼特定情境下]，遇到了 [什麼具體困難]，導致了 [什麼壞結果/浪費了什麼資源]。」


### 思考練習：痛點健康檢查
請回答你的專案想解決的問題：

我的描述裡有沒有出現任何技術或工具名稱？（如果有，請塗掉，只寫想解決的問題，而不是少了什麼工具）

這個問題是「你自己想像的」，還是你「真的採訪/觀察過兩三個你的目標客群」發生的？

用一句話說明：解決這個問題後，使用者能省下什麼（時間/錢）或獲得什麼（便利/快樂）？

## 2. 軟體設計的起點：我們怎麼把想法想成一個系統

有寫過程式或是做過專案的同學可能遇過，我想從頭開始設計一個系統，該從哪裡開始？

在 AI 時代，快速製作 Prototype 的成本大幅降低，「先做再說，再根據結果調整」已經成為很實用的開發方式。
但是當團隊需要討論、你腦中的想法非常巨大，沒辦法純靠現做再看去滿足的話，這時，我們需要一些方法，把腦中的想法轉化成可以分析、討論與驗證的內容。

接下來我們繼續用前面那個偉大的國家級專案：

> 台灣人不能飛 → 蓋一個**傳送門**

### 2-1. 第一個作品：先用 Prototype-First 就好

先講結論：**如果這是你的第一個作品，你預設用的就是 Prototype-First——先做一個最陽春、能動的版本，再邊用邊改。** 這對新手來說是最好的選擇，不是偷懶。

但「先做」之前，至少花三分鐘把使用者會走的路寫下來，不然 AI 跟你都不知道要做什麼。四步就夠：

| 步驟 | 使用者做什麼？ | 系統做什麼／使用者看到什麼？ |
| --- | --- | --- |
| 1 | 走到捷運站旁的傳送門，說「我欲去士林夜市」 | 辨識台語，顯示「目的地：士林夜市，確認？」 |
| 2 | 說「著」或按確認 | 檢查士林那邊的傳送門有沒有人卡著 |
| 3 | 拿著鹹酥雞走進門 | 掃描人＋鹹酥雞，倒數 3 秒 |
| 4 | 走出門 | 人在士林夜市，顯示「傳送完成，耗時 8 秒」 |

> 寫不出四步？通常代表你還不知道使用者要「完成什麼事」，回去看一下第 1 節的問題句。

### 練習：我的 4 步使用流程

### 2-2. 還有其他想法或是根本沒想法呢：想法大到「做了再看」撐不住的時候

如果你已經有一些實作經驗、想做的東西比較大，或是要跟別人一起討論，可以試試下面這些我常用的思維模式。**不用六種都用，看你手上已經有什麼，挑一種當起點。**

| 你手上已經有… | 用這個模式 | 先回答的問題 | 丟給 AI 的一句追問 |
| --- | --- | --- | --- |
| 一堆資料、物品、紀錄 | **Data-First** | 有哪些東西？各自有什麼屬性？怎麼分類？ | 「這些資料之間有什麼關係？我漏了哪些欄位？」 |
| 很清楚的使用者 | **User-First** | 誰會用？他現在卡在哪？ | 「這類使用者還可能遇到哪些我沒想到的狀況？」 |
| 一個每天都在跑的流程 | **Workflow-First** | 從頭到尾有哪些步驟？哪一步最浪費時間？ | 「這個流程哪一步最適合自動化？為什麼？」 |
| 一個很具體的畫面或時刻 | **Scenario-First** | 什麼時候、什麼狀況下，使用者打開它要做什麼？ | 「幫我列出這個情境下可能出錯的三種狀況。」 |
| 一個想改善的數字 | **Goal-First** | 我想改善什麼？怎麼知道有改善？ | 「這個目標可以用什麼數字衡量？哪個最容易量？」 |
| 什麼都沒有，只有一個感覺 | **Prototype-First** | 我可以先做出什麼來試試看？ | 「最小、最快能做出來試的版本是什麼？」 |

六種模式用起來長怎樣（展開看）

趕早八的大學生、通勤的上班族、騎山豬的阿嬤。
阿嬤最痛的其實不是路遠，是路口一直紅燈。那就有了要設計配合的方向。

說目的地，因為要聽得懂台語、客語、原住民語、國語。

- **Scenario-First**：早上 7:65，人還在板橋，早八在三峽 8:10 點名，系統應該做什麼？

我要站在捷運站旁的傳送門，說「我欲去士林夜市」，它要聽得懂台語、客語、原住民語、國語，然後顯示「目的地：士林夜市，確認？」。我按下確認，它要檢查士林那邊的傳送門有沒有人卡著，然後倒數 3 秒，我就出現在士林夜市。
</details>
<details>
<summary>如果你有明確的目標</summary>

- **Goal-First**：希望通勤從 50 分鐘變成 10 秒。怎麼量？計時，然後跟捷運比。

將這個目標拆成子目標：傳送門要能承受阿嬤騎機車的撞擊、要能辨識台語、客語、原住民語、國語、要能傳送人、衣服、鹹酥雞、豆花。每個子目標都可以拆成功能。
</details>
<details>
<summary>如果你真的不太確定，但是很會做東西、手邊有 AI</summary>

- **Prototype-First**：先做一個「對著它說目的地，它會回你一句話」的假傳送門，看大家會不會真的對它講話。

然後使用後，再自己想想慢慢加上「它會聽懂台語、客語、原住民語、國語」、「它會傳送人、衣服、鹹酥雞、豆花」、「它能承受阿嬤騎機車的撞擊」。但是但是這些功能都要先做一個最陽春、能動的版本，再邊用邊改。還有記得在要發展成正式專案時，要把這坨疊出來的功能重新拆解成模組，才不會變成一坨爛泥。

</details>

你會發現：**同一個專案，不同起點會長出不同的設計重點。** 沒有哪個最正確，挑你最有把握的那個開始。

## 3. 新手的三個問題：有沒有人要？做不做得出來？做不做得完？

不管你剛剛是用六種模式畫出了一個完整系統，還是只寫了 4 步流程，現在都要過三關。

> 第 2 節是把想法**展開**；這一節是把它**收回來**。

很多第一個作品不是死在技術，而是死在這三題其中一題。我們的傳送門也逃不掉。

### 3-1. 第一關：有沒有人要？

如果你是做給自己用的，**第一個使用者就是你自己**，這完全沒問題。但你要誠實回答：

> 我真的會每週用它嗎？還是只是覺得「做出來應該很酷」？

如果是做給別人用的，就去問。不用問卷，找三個人問一句就好：

> 「你今天怎麼來學校的？花多久？哪一段最煩？」

注意，問的是**他們現在怎麼處理**，不是「如果有傳送門你會用嗎」。後者每個人都會說會，然後你就會得到一個完全沒用的答案。

<details>
<summary>不寫程式也能驗證「有沒有人要」</summary>

在寫第一行程式之前，你可以先用很便宜的方式假裝產品已經存在：

| 方法 | 怎麼做 | 傳送門版本 |
| --- | --- | --- |
| 假畫面 | 用 Canva、Figma 甚至紙筆畫出畫面，拿給別人「點點看」 | 畫一個傳送門的操作畫面，看阿嬤看不看得懂 |
| 人工假裝系統 | 用 Google 表單收需求，背後其實是你手動處理 | 「傳送鹹酥雞」表單，背後其實是你騎車去買。恭喜，你發明了外送 |
| 先找現成工具 | 搜尋一下有沒有人做過，用用看哪裡不好 | 捷運、YouBike、Uber、外送平台已經解決了多少？剩下沒解決的是什麼？ |

如果現成工具已經解決得很好，那也很好，你省下了一個月。如果它哪裡不好用，那個「不好用」就是你的專案亮點。
</details>

### 3-2. 第二關：我做不做得出來？

把你 4 步流程（或系統草圖）裡的每個功能，標上一個燈號：

| 燈號 | 意思 |
| --- | --- |
| 🟢 | 我會做，或是做過類似的 |
| 🟡 | 我不會，但查得到教學／AI 能帶我做 |
| 🔴 | 我完全不知道這要怎麼做 |

| 傳送門的功能 | 燈號 | 備註 |
| --- | --- | --- |
| 顯示「目的地：士林夜市，確認？」 | 🟢 | 就是一個畫面 |
| 國語語音辨識 | 🟡 | 有現成的語音 API |
| 台語、客語、原住民語語音辨識 | 🟡／🔴 | 查得到研究，但資料少很多 |
| 能承受阿嬤騎機車的撞擊 | 🟡 | 這比較是土木系的事 |
| 傳送鹹酥雞 | 🔴 | ？ |
| 傳送人 | 🔴🔴🔴 | 物理系說要再等等 |

**🔴 不是不能做，而是要最先處理。** 拿 30 分鐘做一個只為了回答「這做得出來嗎」的小實驗（工程師叫它 spike）。例如：找一個台語語音辨識的服務，錄五句「我欲去士林夜市」，看它聽對幾句。

做得出來，安心；做不出來，趁早換方法或砍掉，總比做到最後一週才發現好。

至於「傳送人」——有些 🔴 不是 30 分鐘能驗證的，那種紅燈的意思就是：**這一版先不要。** 記住這件事，第 5 節會用到。

參考用 prompt：

```text
我想做的作品是：［問題句＋4 步流程］。
我是程式新手，主要會用 AI 協助寫程式。

請不要寫程式。請：
1. 列出這個作品需要用到的技術或工具；
2. 標出哪一塊對新手來說最難、最可能卡住；
3. 建議一個 30 分鐘內可以完成、用來確認「最難那塊做不做得出來」的小實驗。
```

### 3-3. 第三關：我做不做得完？

這題最常被跳過，也最常讓作品死掉。要回答它，我們需要一點點專案管理。

### 練習：三關健康檢查

- 第一關：第一個使用者是＿＿＿＿＿＿；我（或他）現在怎麼處理這個問題：＿＿＿＿＿＿
- 第二關：我的 🔴 是＿＿＿＿＿＿；我的 30 分鐘小實驗是＿＿＿＿＿＿
- 第三關：👇 下一節一起算

## 4. 通識版專案管理：範疇與行程

還記得第 0 節說專案就是三件事嗎？

- 我要完成什麼 → **範疇（Scope）**
- 什麼時候要完成 → **時間（Schedule）**
- 我有多少資源可以用 → **資源（Resources）**

這三個互相拉扯，業界叫它「專案鐵三角」。剛好對上我們的三個問題：

| 新手問題 | 鐵三角 | 你的第一個作品 |
| --- | --- | --- |
| 有沒有人要？ | 範疇：哪些東西值得做 | 可以調 |
| 做不做得出來？ | 資源：能力、工具、AI | 短期內改不了 |
| 做不做得完？ | 時間 | 學期中，每週就那幾小時 |

所以結論很殘酷也很簡單：

> **時間和能力都動不了，你唯一能調的只有範疇。**

### 4-1. 範疇：要做的，加上明確不做的

範疇不只是「我要做什麼」，更重要的是「**我這次不做什麼**」。

沒寫下來的範疇會偷偷變大：「欸傳送門順便可以傳豆花好了」「欸要不要加個傳送到日本的國際版」……這叫 **Scope Creep（範疇蔓延）**，是個人專案的頭號殺手。每多一個「順便」，截止日就默默往後跑一點。

### 4-2. 行程：不用甘特圖，用時間預算

做第一個作品不需要甘特圖。你只需要算一個數字：

```text
每週可以投入的小時數 × 週數 ＝ 我的總時間預算
```

例如：每週 4 小時，打算 4 週做完，但要留 1 週緩衝，所以是 4 小時 × 3 週 ＝ **12 小時**。

記住兩個新手生存法則：

1. **估時直接乘 2 到 3。** 你覺得 2 小時能做完的東西，加上裝環境、查錯誤、AI 寫錯重來，通常要 4 到 6 小時。這不是你特別慢，大家都這樣，工程師也是。
2. **預留一週緩衝。** 期中考、報告、社團活動一定會來。

再送一個觀念：**時間盒（Timebox）**。截止日先定死，做不完就砍範疇，不要延期。延期一次就會延期第二次。

### 練習：我的時間預算

| 項目 | 填寫 |
| --- | --- |
| 每週可以投入幾小時？ |  |
| 我想在幾週內完成第一版？ |  |
| 扣掉一週緩衝後的總時間預算 |  |
| 第一版截止日 |  |

## 5. MVP：把範疇縮到三關都過

算出時間預算之後，MVP 就自己跑出來了。

### 5-1. MVP 是算出來的

把你想做的功能全部列出來，**從最重要的往下排**，估時乘 2 到 3 之後一路往下加，加到超過時間預算的那一刻，畫一條線。

傳送門的時間預算是 12 小時，開始排：

| 順序 | 功能 | 估時（已乘 2～3） | 累計 |
| --- | --- | --- | --- |
| 1 | 傳送人 | ∞ | ∞ |

……好，第一列就爆了。

這時候不是放棄，而是回到第 1 節：**痛點是「通勤太久、太麻煩」，傳送門只是我們想到的其中一種解答。** 傳送不了人，那在 12 小時內，什麼東西能讓通勤變輕鬆一點？

| 順序 | 功能 | 估時（已乘 2～3） | 累計 |
| --- | --- | --- | --- |
| 1 | 用國語說出目的地，顯示確認畫面 | 3 小時 | 3 |
| 2 | 查出去那裡最快的方式（捷運／公車／YouBike）和時間 | 4 小時 | 7 |
| 3 | 告訴你「幾點前出門才不會遲到」 | 2 小時 | 9 |
| 4 | 聽得懂台語 | 3 小時 | 12 |
| ─ | **時間預算 12 小時，畫線** | ─ | ─ |
| 5 | 客語、原住民語 | 6 小時 | 18 |
| 6 | 承受阿嬤機車撞擊的外殼 | 要找土木系 | ─ |
| 7 | 傳送鹹酥雞、豆花 | ∞ | ─ |
| 8 | 傳送人 | ∞ | ─ |

**線上面的就是你的 MVP，線下面的放進停車場。** 名字可以繼續叫「傳送門 v0.1」，沒人會阻止你。

> 停車場不是垃圾桶。被砍掉的點子不是刪掉，是留給第二版。做完 MVP 之後，你會比現在更知道停車場裡哪個最值得做。（物理系做出來的那天，傳送人就從停車場開出來了。）

### 5-2. MVP 不是簡陋版

MVP（Minimum Viable Product，最小可行性產品）不是「什麼都做一點點的爛版本」，而是**用最少功能，完成最核心的那件事**。

| 傳送門 | 第一版做 | 這次不做（停車場） |
| --- | --- | --- |
| 移動 | 告訴你最快怎麼到、幾點出門 | 真的把你傳過去 |
| 語言 | 國語＋台語 | 客語、原住民語（下一版優先） |
| 物品 | 不處理 | 鹹酥雞、豆花（豆花會灑） |
| 耐撞 | 它是手機上的網頁，不怕撞 | 阿嬤機車規格外殼 |

一個簡單的檢查方法：

> **「如果只剩一個週末，我仍然要完成＿＿＿＿。」**

傳送門的答案：說出目的地，就知道幾點出門、怎麼走最快。空格裡的那件事，就是你 MVP 的心臟，其他都可以等。

> 需求是「通勤更輕鬆」；傳送門只是其中一種解法。**不要把解法誤當成需求**，你的 MVP 才有機會活下來。

### 5-3. 小心「AI 幫我決定」

很多人到這一步會直接問 AI：「幫我規劃一個傳送門的 MVP」。AI 會很熱心、很認真地給你一份包含量子糾纏模組的完整清單，然後你就會得到一個做不完的 MVP。

> **你決定：問題、優先順序、MVP 範圍。AI 協助：追問、比較、實作。**

AI 不知道你每週只有 4 小時，也不知道你最在意的是哪件事。這些只有你能決定。

使用者（或我自己）最重要的價值：＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿

如果只剩一個週末，我仍然要完成：＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿

## 6. 把 MVP 切成一步一步

MVP 有了，但「做一個傳送門 v0.1」還是太大，你打開電腦還是不知道第一步要幹嘛。所以要再切。

### 6-1. 橫著切 vs 直著切

上一課我們把**程式**拆成介面、規則、資料、回饋；這一課我們要拆的是**工作**。新手最常見的切法是橫著切：

```text
❌ 橫著切（一層一層做）
第一週：把所有畫面做完
第二週：把語音辨識、查路線全部寫完
第三週：把資料存取做完
第四週：串起來……然後發現什麼都接不起來
```

```text
⭕ 直著切（一條一條做）
切片 1：說「我要去士林夜市」→ 畫面顯示「目的地：士林夜市」  ← 做完就能跑
切片 2：按確認 → 顯示最快的路線和時間                       ← 做完就能跑
切片 3：顯示「幾點前出門才不會遲到」                         ← 做完就能跑
切片 4：說台語也聽得懂                                       ← 做完就能跑
```

直著切的每一片，都穿過介面、規則、資料、回饋，**做完就是一個能動、能展示的東西**。就算你只做完前兩片就被期末考打斷，你手上還是有一個能用的傳送門 v0.1，而不是四分之一個什麼都跑不動的專案。

> 不是「先做一個按鈕」或「先建資料庫」，而是讓使用者能完成一小件有意義的事。

### 6-2. 怎麼知道一片做完了？

每一片都要寫上「怎麼知道做完了」，不然你會在同一片裡面一直改一直改。

```text
❌ 做好語音功能
✅ 用國語說「我要去士林夜市」，3 秒內畫面顯示「目的地：士林夜市，確認？」
```

| 驗收案例 | 預期結果 |
| --- | --- |
| 正常情況：說「我要去士林夜市」 | 顯示「目的地：士林夜市，確認？」 |
| 一個例外情況：說「我要去霍格華茲」 | 顯示「找不到這個地方，請再說一次」，不會當掉 |
| 不應被弄壞的既有行為 | 不想講話的人，用打字輸入目的地還是可以用 |

上一課的驗收表又回來了，因為它在寫程式之前就有用：**先想好怎麼驗收，AI 寫完你才知道要檢查什麼。**

### 練習：我的切片清單

把線上面的 MVP 切成 4 到 8 片，每片一句「怎麼知道做完了」。

| 切片 | 使用者能完成的一小件事 | 怎麼知道做完了 | 燈號 |
| --- | --- | --- | --- |
| 1 |  |  |  |
| 2 |  |  |  |
| 3 |  |  |  |
| 4 |  |  |  |

> 🔴 的那片，記得用第 3-2 節的 30 分鐘小實驗先戳一下。

<details>
<summary>進階：從系統草圖切</summary>

如果你在第 2-2 節畫了系統草圖，可以直接用草圖找切片：

- **Data-First**：先切「一種資料能完整存進去、讀出來、顯示出來」的那一片。例如先只處理「目的地」這一種資料。
- **Workflow-First**：先切流程裡「第一步到最後一步都有、但每步都最陽春」的那一條（工程師叫它 Walking Skeleton，走路骨架）。例如：打字輸入目的地 → 顯示一條寫死的路線 → 顯示出門時間，全部都很假，但整條路是通的。
- **Scenario-First**：一個情境就是一片。「早上 7:50 還在板橋」就是一片。

另外，切片之間有先後依賴的話，寫上「要先完成什麼」。被很多片依賴的那片，就是你最該先做的。
</details>

## 7. 開工：一份給人也給 AI 看的 README

到這裡，你手上已經有：問題句、4 步流程、三關檢查、時間預算、MVP 和停車場、切片清單。把它們放在同一個地方，就是你專案的 **README**。

### 7-1. README 為什麼重要？

README 是一個專案的門面，放在 GitHub 上別人第一眼就會看到它。但它其實有三個讀者：

| 讀者 | 他要從 README 知道什麼 |
| --- | --- |
| 未來的你 | 我當初為什麼要做這個？做到哪了？下一步是什麼？ |
| AI | 這個專案是什麼、範圍在哪、哪些東西不要幫我加 |
| 別人（同學、面試官、評審） | 這個作品解決什麼問題？怎麼用？做得怎麼樣？ |

**第二個讀者很多人會忘記。** 每次開新對話叫 AI 幫忙，都要重新解釋一次專案嗎？不用，把 README 貼給它就好。你也可以把它放進 ChatGPT 的 Projects、Gemini 的 Gems，或是 AI coding 工具的專案說明檔（例如 `CLAUDE.md`、`AGENTS.md`），讓 AI 每次都先讀過。

這樣它就不會在你做傳送門 v0.1 的時候，突然幫你加上量子糾纏模組。

### 7-2. README 模板

直接複製，把今天的練習貼進去：

```markdown
# 專案名稱

## 這是什麼？
一句話：［問題句］

## 30 秒 demo
打開後我能＿＿＿＿，然後看到＿＿＿＿。

## 使用流程
1.
2.
3.
4.

## 第一版範圍
- 做：
- 這次不做（停車場）：

## 時間預算
每週＿小時 × ＿週，第一版截止日：＿＿＿＿

## 切片與進度
- [ ] 切片 1：＿＿＿＿（完成標準：＿＿＿＿）
- [ ] 切片 2：
- [ ] 切片 3：

## 給 AI 的注意事項
- 我是程式新手，請先解釋計畫再寫程式。
- 不要加入「這次不做」裡的功能。
- 每次只做一個切片。
```

### 7-3. 放上 GitHub

不用打開終端機，網頁版就可以完成：

1. GitHub 右上角 `+` → **New repository**，取個名字，勾選 **Add a README file**。
2. 點開 README → 右上角鉛筆圖示 ✏️，貼上剛剛的內容 → **Commit changes**。
3. 到 **Issues** 分頁，**每個切片開一個 Issue**。標題寫切片，內容寫完成標準。

> 一個切片＝一個 Issue。做完一片，關掉一個 Issue，你會很清楚看到自己的進度在前進，這件事對撐完一個專案很重要。

想用指令的同學，可以翻第五課的 Git 指令表，再加上這三個：

```shell
# 開一條新分支來做某個切片
git switch -c slice-1
# 把本機的提交推上 GitHub
git push
# 把 GitHub 上的最新版本拉下來
git pull
```

> ⚠️ 不管用哪種方式：**API Key、密碼絕對不要 commit 上去。** 公開 repo 上的金鑰，幾分鐘內就會被機器人掃走。

### 7-4. 讓 AI 當規劃夥伴

README 寫好之後，先別急著叫 AI 寫程式。先讓它當你的規劃夥伴挑毛病：

```text
這是我的專案 README：［貼上］

請不要寫程式。請：
1. 問我最多 5 個最能縮小範圍的問題；
2. 檢查我的切片是不是「直著切」，每片做完都能跑；
3. 指出哪一片的完成標準太模糊；
4. 根據我的時間預算，告訴我最可能做不完的地方；
5. 標示你做出的假設。
```

確認沒問題之後，再開始第一個切片：

```text
這是我的專案 README：［貼上］
我現在要做切片 1：［內容］，完成標準是：［內容］。

請先提出計畫，不要直接寫完整專案：
1. 這個切片需要建立或修改哪些檔案，各自負責什麼；
2. 可以一步一步完成的小步驟；
3. 我要怎麼測試它符合完成標準。
```

檢查 AI 的答案：它有沒有偷加你說過不做的功能？它是不是一次想做完好幾個切片？哪一項是假設而不是事實？

<details>
<summary>回到開頭的問題：專案沒有交作業的按鈕，那怎樣才算「做完」？</summary>

作業交出去就結束了，但作品要「別人真的能用」，還有幾件事要想。第一版不一定全部要有，但至少知道它們存在：

| 問題 | 第一版可以怎麼做 |
| --- | --- |
| 別人要怎麼用到它？（部署） | 網頁可以先用 GitHub Pages、Vercel 等免費服務；小工具可以附上安裝與執行說明 |
| 資料存在哪裡？ | 先存在本機或一個檔案就好，確定需要再上資料庫 |
| 有用到 API Key 嗎？（例如語音辨識、查路線） | 放在環境變數或 `.env`，並把 `.env` 加進 `.gitignore` |
| 免費額度用完會怎樣？ | 先查一下你用的服務每月免費多少，超過會不會自動扣錢 |
| 壞掉了我怎麼知道？ | 至少留一個讓使用者回報問題的地方（Issue、表單、你的 IG） |
| 別人看得懂怎麼用嗎？ | README 加上截圖和使用步驟 |

**作品要能被看見。** 一個好的作品集 README，除了上面的模板，通常還會有：一張截圖或 GIF、一個能點的 demo 連結、一段「我做這個學到什麼」。面試官跟評審通常不會 clone 你的程式來跑，他們只會看 README 三十秒。
</details>

## 收尾：讓專案真的開始

今天的終點不是做完一個 App，而是讓你的作品不再只停在腦中。

```text
想法 → 問題句 → 4 步流程（或系統草圖）
→ 三關：有沒有人要？做不做得出來？做不做得完？
→ 範疇＋時間預算 → MVP＋停車場
→ 直著切 → README → 第一個 Issue → 開工
```

### 回去後的第一週

1. 把 README 放上 GitHub，切片開成 Issue。
2. 做完你的 30 分鐘小實驗（如果有 🔴 的話）。
3. 開始切片 1，做完就關掉第一個 Issue。

> **第一個作品，做完比做大重要。** 做完一個小東西，你會學到的比規劃一個大東西多十倍。台灣人今天還是不能飛，但至少不會遲到了。

### 跟社團小專案的關係

今天練的是**一個人**怎麼把想法變成作品。你在社團小專案裡會遇到另一半：**一群人**怎麼一起做，像是怎麼分工、怎麼用 PR 讓別人檢查你的修改、怎麼不把彼此的程式改壞。那些會由各組的技術幹部帶著大家實際走一遍。

如果你今天還想不到自己的題目，也可以先用你所屬小專案的主題，把今天的練習走一遍，方法是一樣的。
