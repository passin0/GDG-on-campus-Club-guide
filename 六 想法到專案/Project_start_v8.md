# GDG 上學期社課｜從想法到專案：你的第一個作品，從一句話到會動


> 第一個作品，做完比做大重要。

上一堂課，我們學會當「監工」：看懂 AI 寫好的專案，知道哪裡漏水該找誰修，再安全地改它。
這一堂課要換你自己開工。

你可能是這幾種人之一：

```text
「我想做點東西，但不知道要做什麼。」
「我有想法了，但不知道第一步是什麼。」
「我叫 AI 做了，但做出來的不是我要的。」
「我開過專案……然後它就一直躺在資料夾裡。」
```

今天我們要從你腦中的一句話出發，一路走到一個**醜，但會動**的第一版。
中間會借用一點軟體工程和專案管理的常識，但每一段都會有你轉頭就能用在自己作品上的東西。

##### 出發前小提醒：今天不會教你任何「神級 prompt」，也不需要你先會寫程式。你會帶走的是一套「把想法變成可以開工的專案」的方法，不管你用 ChatGPT、Gemini、Claude Code、Cursor 還是 Antigravity 都通用。

## 今天的任務

下課時，你會帶走這些東西：

```text
📌 一個題目（從你自己的痛點來）
📌 一個不寫 code 的驗證方法
📌 三層目標＋一張不做清單
📌 一張 breadboard（粗略的畫面流程）和元素清單
📌 一份 SPEC.md（含驗收條件）
📌 一個 Spike 的結論：🟢／🟡／🔴
📌 一個會動的骨架，以及你的第一個 commit
```

而且你能：

- 分辨「我覺得有人需要」和「我有證據有人需要」；
- 說清楚這次要做什麼、**不做什麼**；
- 寫出一份 AI 和人都看得懂的規格；
- 讓 AI 先想、先列計畫，而不是直接開寫；
- 先打通一個最陽春的版本，再慢慢變好。

今天有兩個貫穿範例：

| 範例 | 用在哪 | 為什麼 |
| --- | --- | --- |
| 📚 北大二手教科書交換 | 第 0–2 節：想法和驗證 | 每學期都有人想做，很適合拿來檢查「到底有沒有人要」 |
| 🍱 三峽午餐輪盤 | 第 3–10 節：從規劃到動手 | 自己就是使用者，適合當第一個作品從頭走一遍 |

## 0. 想法是「注意到」的，不是「想出來」的

很多人坐在電腦前想：「我要做什麼 App 才會紅？」然後想出一堆聽起來很酷、但沒人需要的東西。

矽谷創業加速器 Y Combinator 的創辦人 Paul Graham 寫過一篇很有名的文章〈How to Get Startup Ideas〉。他的建議很簡單：**好點子不是想出來的，是注意到的。** 最好的點子，通常來自你自己真的遇過的問題。

### 0.1 痛點日記

接下來一週，每次你遇到下面這些情況，就記下來：

```text
😤 我又在抱怨……
🔁 這件事我每週都要重複做一次，好煩……
🤷 為什麼沒有人做一個……
📝 我用了一個很爛的土法煉鋼方法在解決……
```

最後一種最有價值。**如果你已經用 Excel、LINE 記事本、截圖相簿在硬撐一件事，那代表這個問題是真的。**

### 0.2 篩選你的點子

把痛點日記裡的點子拿來打分數：

| 點子 | 多常發生？ | 多痛？ | 現在怎麼解決？ | 我自己會用嗎？ |
| --- | --- | --- | --- | --- |
| 二手教科書交換 | 每學期初一次 | 中（課本很貴） | 臉書社團、學長姐直接給 | 可能會 |
| 社團器材借用登記 | 每週 | 中（常找不到誰借走） | LINE 群組問 | 會 |
| 午餐決定器 | 每天 | 低 | 隨便選 | 會 |

沒有標準答案，但如果某一欄你寫不出來，就是你該去調查的地方。

<details>
<summary>麻煩的事，反而是機會（打開看看）</summary>

Paul Graham 還有另一篇文章叫〈Schlep Blindness〉。Schlep 是「又累又煩的苦差事」的意思。

他的觀察是：人的大腦會自動忽略那些「做起來很麻煩」的點子，連想都不去想。但正因為大家都避開，那些麻煩的問題反而沒人解決，是很好的機會。

所以當你想到一個點子，第一個反應是「這好麻煩喔」的時候，先別急著跳過。

</details>

## 1. 不寫 code，也能知道有沒有人要

這是今天最有趣的部分之一：**你可以在不寫一行程式的情況下，測試一個「產品」。**

### 1.1 先找出最危險的假設

每個點子，其實都是一串「**我相信……**」疊起來的。以二手教科書為例：

```text
- 我相信學長姐願意把上學期的舊書拿出來賣
- 我相信大家覺得在臉書社團找書很麻煩
- 我相信找二手書真的很困難
```

只要其中一個是錯的，整個點子就會垮。

先挑「**錯了點子就會死，而且你現在還沒有證據**」的那一條來測。
以二手書來說是第一條：平台最怕的是有人要買、沒人要賣，沒有書，買家來一次就不會再來了。

### 1.2 四種方法

| 方法 | 怎麼做 | 使用者知道是人工嗎？ | 經典例子 |
| --- | --- | --- | --- |
| 🙋 **人肉服務**（Concierge） | 你親自手動提供服務 | 知道 | 你親自幫人配對買賣 |
| 🧙 **綠野仙蹤**（Wizard of Oz） | 前台看起來像產品，後台是你在手動處理 | 不知道 | Zappos |
| 🚪 **預告頁**（Fake Door／Smoke Test） | 做一個介紹頁，看多少人點「我要用」 | 點了才知道還沒上線 | 很多新創上線前都會做 |
| 🎬 **影片 Demo** | 做一支影片展示「如果有這個產品」 | 知道 | Dropbox |

<details>
<summary>經典例子的故事（打開看看）</summary>

**Zappos（網路鞋店）**：創辦人想知道「大家願不願意在網路上買鞋」。他沒有先建倉庫、進貨，而是去附近的鞋店拍照、放上網站。有人下單，他就去店裡用原價買下來，再寄給客人。每一筆都賠錢，但他用很便宜的方式證明了「有人願意在網路上買鞋」。

**Dropbox（雲端硬碟）**：雲端同步的技術很難做，要花很久。創辦人 Drew Houston 先做了一支幾分鐘的影片，展示「如果有這個產品，會長什麼樣子」，附上等待名單，發到科技社群。等待名單暴增，證明大家真的想要，才放心投入開發。

兩個例子都在回答同一個問題：**在花大錢、大時間之前，先確定有人要。**

</details>

### 1.3 二手教科書可以怎麼測？

| 要測的假設 | 方法 | 具體做法 | 工具 |
| --- | --- | --- | --- |
| 學長姐願意賣舊書 | 🙋 人肉服務 | 在系群發「舊書收集」表單 | Google 表單 |
| 大家覺得臉書社團找書很麻煩 | 🚪 預告頁 | 做一頁「依課號找二手書」的介紹，放「通知我上線」按鈕 | Google Sites、Carrd |
| 找二手書很困難 | 🧙 綠野仙蹤 | 做一個「輸入課號，我們幫你找」的表單，後台你自己去社團翻 | Google 表單 + 你自己 |
| 會不會真的完成交易 | 🙋 人肉服務 | 你親自當媒合人，用 LINE 把買家和賣家拉在一起 | LINE、試算表 |

最後一種最真實。如果你親自媒合了 10 筆交易，你會學到一大堆你坐在電腦前永遠想不到的事：

```text
- 原來大家最在意的是「書上有沒有劃記」
- 原來很多人只想買「上一屆的版本」
- 原來面交最大的問題是「約不到時間」
- 原來大部分交易都集中在開學前兩週
```

這些都會變成你之後寫程式時的**規格**。

### 1.4 小提醒

- **預告頁要誠實**：使用者點了「我要用」之後，要清楚告訴他「我們還在準備中，留下 email 會第一個通知你」，不要讓人覺得被騙。
- **點「通知我」只代表好奇，不代表會用**。如果可以，讓對方多付出一點（例如填寫他要賣的書名），訊號會更準。
- **人數不用多**。你要的是學習，不是漂亮的數字。認真跟 5 個填表單的人聊一聊，比數到 100 個 email 有用。

### 🧪 換你設計

幫你最危險的假設，選一種不寫 code 的方法，寫下三件事：

```text
1. 我要用什麼方法？
2. 我要觀察什麼？（數什麼、看什麼行為）
3. 怎樣算成功？（先寫好數字和期限，例如「一週內有 15 本書被登記」）
```

**限制：這個實驗要能在 48 小時內開始執行。**

## 2. 這時候，才開始寫 code

通過驗證之後，你終於可以開始寫程式了。
但這時候的你，跟一開始的你完全不一樣：

| 一開始的你 | 現在的你 |
| --- | --- |
| 「我覺得大家需要一個二手書平台」 | 「我知道學長姐願意賣，而且買家最在意劃記程度」 |
| 功能清單有 20 項 | 只做被證明有需要的 3 項 |
| 不知道要先做什麼 | 從人肉服務裡最痛的那一步開始自動化 |

### 2.1 從人肉服務到程式

最好的起點，是**你手動做最累的那一步**。

```text
你手動做的事                       → 第一個要寫的程式
每天整理表單、配對買家賣家         → 依課號自動列出可買的書
一直被問「書況怎樣」               → 賣家上架時勾選劃記程度
```

- 參考用 prompt：

```text
我在做一個［點子］。以下是我驗證過的事實：
- ［實驗中學到的事］
- ［實驗結果］
- ［使用者最在意的事］

我目前手動在做的流程是：［描述］。
請先不要寫程式。幫我規劃一個「只自動化最累那一步」的最小版本：
1. 需要哪些功能（最多 3 個）；
2. 哪些事情可以繼續手動做；
3. 用什麼工具最簡單（不一定要寫程式，試算表也算）。
```

注意第 2、3 點：**不是每件事都要寫程式**。有時候一個 Google 試算表加上表單，就能撐很久。

### 2.2 如果你只是想做一個練功的作品？

不是每個作品都要有「市場」。如果你只是想做一個給自己用、或練習技術的作品，偵探的問題可以改成：

```text
❓ 我自己真的會用嗎？（用一週看看）
❓ 我身邊有沒有一個人也會用？（找他用一週看看）
❓ 做完之後，我能拿它跟別人講出一個好故事嗎？（作品集、面試）
```

**自己就是第一個使用者，也是一種驗證。** 只是你要對自己誠實。

接下來，我們就用一個「自己就是使用者」的作品，把剩下的路從頭走一遍：
**🍱 三峽午餐輪盤**——每天中午跟室友糾結吃什麼的你，就是它的第一個使用者。

## 3. 這次做什麼、不做什麼

### 3.1 Good／Better／Best

哈佛大學的 CS50 是全世界最有名的程式入門課之一。它的期末專題要求學生替自己的作品訂**三層目標**：

| 層級 | 意思 |
| --- | --- |
| **Good** | 不管發生什麼事，一定要做到的 |
| **Better** | 正常情況下，覺得做得到的 |
| **Best** | 一切順利的話，希望做到的 |

午餐輪盤的三層目標：

| 層級 | 內容 |
| --- | --- |
| Good | 能新增、刪除口袋名單裡的店家，按「抽！」隨機抽出一家 |
| Better | 最近 3 天吃過的店不會被抽到；室友的手機也看得到同一份名單 |
| Best | 可以只抽某一類（今天想吃麵）、室友一起投票 |
| **不做** | 登入、串 Google Maps、評分和留言、App 上架 |

這張表的厲害之處在於：**就算你只做到 Good，你也「完成」了一個作品。**
而不是「做了一半的 Best」。

### 3.2 MoSCoW：另一種排序法

業界也常用 **MoSCoW** 來排功能的優先順序：

| 類別 | 意思 | 對應 |
| --- | --- | --- |
| **M**ust have | 沒有就不能用 | Good |
| **S**hould have | 很重要，但沒有也能用 | Better |
| **C**ould have | 有的話很好 | Best |
| **W**on't have（this time） | 這次不做 | 不做清單 |

新手最常犯的錯：**什麼都標 Must**。
如果你的 Must 清單太長，就砍一半。真的。

### 3.3 不做清單：你給自己的煞車

為什麼要特別寫「不做」？
因為做的過程中，你一定會冒出「啊，順便加一下這個好了」的念頭。《Shape Up》說得很好：**範疇會像草一樣自己長出來。** 這不是誰的錯，是專案的天性。

不做清單就是你的除草機。每次想加功能，先看一下這張清單：**它在上面嗎？在上面就不做。**

## 4. 粗略塑形：畫到剛剛好就停

知道這次要做什麼、不做什麼之後，接下來要決定它「大概長什麼樣子」。
但這時候**不要**開 Figma 畫精美的設計圖，也不要叫 AI 直接寫程式。

《Shape Up》建議兩個工具，刻意讓你**畫不出細節**：

### 4.1 Breadboard（麵包板圖）

名字來自電子工程的麵包板：上面有零件和電線，但沒有外殼。
只用文字和箭頭，畫出三種東西：

| 元素 | 是什麼 | 怎麼畫 |
| --- | --- | --- |
| **地點** | 使用者會去的畫面、頁面 | 文字加底線 |
| **可操作的東西** | 按鈕、輸入框、文字 | 寫在地點下面 |
| **連線** | 按了之後去哪裡 | 箭頭 |

午餐輪盤的 breadboard：

```text
首頁                          新增店家
‾‾‾‾                          ‾‾‾‾‾‾‾‾
口袋名單（每家店旁邊有刪除）     店名 [____]
[ + 新增 ] ─────────────────→  類型 [飯▼]
[ 抽！ ]                       [ 儲存 ] ──┐
   │     ↑                               │
   │     └───────────────────────────────┘
   ↓
結果
‾‾‾‾
今天吃：阿婆麵
[ 就這家 ] → 記錄下來，回首頁
[ 再抽一次 ]
```

就這樣。沒有顏色、沒有排版、沒有 icon。
但你已經知道：**有三個畫面、幾個按鈕、兩個欄位，以及每個按鈕按下去會去哪裡。**

### 4.2 Fat Marker Sketch（粗筆草圖）

如果你的點子很需要「畫面怎麼排」，就用一支**很粗的麥克筆**（或在平板上把筆刷調到最粗）畫草圖。
筆粗到你**沒辦法畫細節**，就不會陷入「這個按鈕要圓角還是直角」的地獄。

### 4.3 為什麼要刻意畫粗？

| 畫太細 | 畫太粗 | 剛剛好 |
| --- | --- | --- |
| 花太多時間在不重要的細節 | 不知道到底要做什麼 | 知道有哪些畫面、按鈕、流程 |
| 捨不得改 | 每個人想像的都不一樣 | 保留彈性，做的時候可以調整 |
| AI 會照抄你的細節，就算那些細節不好 | AI 會自由發揮 | AI 知道要做什麼，又有空間做好 |

> 塑形的目標：**夠具體，可以開工；夠模糊，保留彈性。**

### 4.4 產出：元素清單

塑形完成後，把結果寫成一張短短的**元素清單**：

```text
午餐輪盤第一版的元素：
- 首頁：口袋名單（可刪除）、「新增」按鈕、「抽！」按鈕
- 新增頁：店名、類型（飯／麵／其他）
- 結果頁：顯示抽到的店，「就這家」記錄後回首頁、「再抽一次」
```

比「做一個午餐 App」具體太多，但又沒有規定任何技術細節。

### 🧪 換你畫

用文字和箭頭，畫出你作品的 breadboard，再寫成元素清單（最多 5 行）。

## 5. 同一句話，三個 App

有了三層目標和元素清單，你可能會想：「好，可以叫 AI 開工了吧？」
先來做個實驗。把這句話丟給 AI 三次（記得每次都開新對話）：

```text
幫我做一個決定午餐吃什麼的 App。
```

你可能會拿到這三種完全不同的東西：

| | 第一次 | 第二次 | 第三次 |
| --- | --- | --- | --- |
| 長相 | 一個轉盤，按下去隨機轉 | 一個有登入、評分、留言的餐廳平台 | 先問你今天心情、預算，再推薦 |
| 資料 | 寫死 5 家店 | 要你接 Google Maps API | 一個很長的問卷 |
| 你的反應 | 太陽春了吧 | 我只是想決定午餐…… | 好像不錯，但我沒說要問卷 |

三個都「能動」，三個都不是你要的。

為什麼？因為你腦中其實有很多沒說出口的決定：

```text
- 店家清單是我自己輸入，還是 AI 去抓？
- 要不要記得我上次吃過什麼，避免連續吃同一家？
- 只有我自己用，還是要跟室友一起投票？
- 手機用還是電腦用？
```

你沒講，AI 就只能猜。而每一次猜的都不一樣。

> **Generate ≠ What I want.** AI 生出來的東西，會「長得像」你要的，但不一定「是」你要的。

GitHub 在 2025 年推出開源工具 Spec Kit 的時候，也講了一樣的觀察：AI agent 很常寫出「看起來對、但其實沒抓到意圖」的程式，問題通常不在 AI 寫程式的能力，而是我們給它的指令太模糊。他們的解法是：**先寫規格，再寫程式。**

### 🧪 換你試試

把你自己的點子用**一句話**丟給 AI 兩次（兩個新對話），比較一下：

| 這兩次哪裡不一樣？ | 這是我原本心裡想的嗎？ | 我其實已經偷偷決定、但沒說出口的事 |
| --- | --- | --- |
|  |  |  |

最右邊那一欄，就是你等一下要寫進規格的東西。

### 5.1 規格是什麼？給人也給 AI 的施工圖

蓋房子不會直接叫工人開始砌磚，會先有一份施工圖：幾房幾廳、門開哪邊、哪裡要插座。
軟體也一樣。

> **規格（Specification，簡稱 Spec）**：一份描述「要做什麼、為什麼做、怎樣算做好」的文件。

注意，規格寫的是 **What（做什麼）** 和 **Why（為什麼）**，**不寫 How（怎麼做）**。
「用 Python 還是 JavaScript」「資料存在哪裡」這些技術決定，是下一步「計畫」的事。

一個 AI 時代的專案，通常會有這幾份文件：

| 文件 | 給誰看 | 寫什麼 | 誰寫 |
| --- | --- | --- | --- |
| `README.md` | 人（使用者、隊友、未來的你） | 這是什麼、怎麼安裝、怎麼用 | 你（可請 AI 潤飾） |
| `SPEC.md` | 你和 AI | 要做什麼、不做什麼、怎樣算做好 | 你主導，AI 幫忙追問 |
| 計畫（Plan） | 你和 AI | 用什麼技術、分哪些模組、資料怎麼存 | AI 提案，你挑選 |
| 任務（Tasks / Issues） | AI 和你 | 一張一張的小工作單 | AI 拆，你審 |
| `AGENTS.md` / `CLAUDE.md` | AI | 這個專案的工作守則 | 你 |

> **Prompt 用完就丟，規格會留下來。**
> 每次開新對話，AI 都會失憶；但只要規格在專案裡，它隨時可以重新讀一遍，理解跟上次一樣的東西。

<details>
<summary>業界的三種「規格先行」流派（打開看看）</summary>

這幾年 AI coding 工具不約而同地走向同一件事：**先規格、後程式**。名字不同，骨架一樣。

| 工具 | 流程 | 產出的文件 |
| --- | --- | --- |
| GitHub Spec Kit（開源） | Specify → Plan → Tasks → Implement | spec、plan、tasks |
| AWS Kiro | Requirements → Design → Tasks | `requirements.md`、`design.md`、`tasks.md` |
| Claude Code（官方建議） | 先讓 AI 訪問你，把結果寫進 `SPEC.md`；用 Plan 模式先規劃再動手 | `SPEC.md`、`CLAUDE.md` |

GitHub 那篇介紹 Spec Kit 的文章有一句話很值得記：過去我們說「程式碼才是唯一的真相」，現在要變成「**意圖才是唯一的真相**」。
程式碼可以重寫，但「你到底想要什麼」必須被好好保存下來。

另外一個重點：規格是**活的**。做到一半發現新東西，先改規格，再改程式。

</details>

## 6. 一頁規格：七個欄位

不用寫成企劃書。一頁、七個欄位就夠了。
前面的三層目標、不做清單和 breadboard，現在都可以直接搬進來。

### 6.1 先看範例

```markdown
# 三峽午餐輪盤 SPEC

## 1. 問題
每天中午跟室友花 15 分鐘討論吃什麼，最後還是吃同一家。

## 2. 誰會用
我自己和兩個室友。用手機打開。

## 3. 這次要做的事（核心功能）
- 我可以自己新增、刪除口袋名單裡的店家
- 按一個按鈕，隨機抽出一家
- 最近 3 天吃過的店，不會被抽到

## 4. 這次明確不做（非目標）
- 不做登入、不做多人帳號
- 不串 Google Maps、不自動抓店家
- 不做評分和留言
- 不做 App 上架，用手機瀏覽器打開就好

## 5. 使用流程
打開網頁 → 看到口袋名單 → 按「抽！」→ 顯示今天吃哪家 → 按「就這家」記錄下來

## 6. 需要記住的資料
- 店家：名字、類型（飯／麵／其他）
- 吃飯紀錄：哪一天吃了哪一家

## 7. 驗收條件
（下一節教你寫）
```

是不是比「幫我做一個決定午餐吃什麼的 App」清楚太多了？

### 6.2 每個欄位在幹嘛

| 欄位 | 回答什麼問題 | 常見錯誤 | 改成這樣 |
| --- | --- | --- | --- |
| 1. 問題 | 為什麼要做？ | 「市面上沒有好用的」 | 寫一個具體情境：誰、在什麼時候、遇到什麼麻煩 |
| 2. 誰會用 | 給誰用？在哪用？ | 「所有人」 | 越具體越好，「我和室友、用手機」 |
| 3. 要做的事 | 使用者能做到什麼？ | 寫技術：「用 React 做前端」 | 寫行為：「我可以……」（可以直接用你的 Good 和 Better） |
| 4. **不做的事** | 這次刻意不碰什麼？ | 空白 | 至少寫 3 條，直接搬你的不做清單 |
| 5. 使用流程 | 一步一步怎麼用？ | 只寫功能清單 | 用箭頭寫出一條從頭到尾的路（照著你的 breadboard 寫） |
| 6. 資料 | 程式要記得什麼？ | 忘了寫 | 想想「關掉再打開，什麼東西要還在？」 |
| 7. 驗收條件 | 怎樣算做好？ | 「要好用」 | 寫成可以檢查對錯的句子（下一節） |

### 6.3 不做清單，寫給 AI 看

第 3 節的不做清單，在這裡會發揮第二個作用：**它也是給 AI 的煞車**。

因為 **AI 超級熱心**。
你說要做午餐輪盤，它可能順手幫你加上登入系統、深色模式、多國語言，還有一個你看不懂的資料庫。
每多一個功能，就多一個會壞的地方。

> **非目標（Non-goals）是你給 AI 的煞車。** 沒寫「不做」，AI 就會一直做。

第五課學過的模組責任也用得上：寫「不做的事」的時候，順便想想「這樣就不需要哪個模組」。不做登入 → 不需要帳號模組；不串地圖 → 不需要外部 API。整個專案瞬間瘦一圈。

### 6.4 寫不出來？讓 AI 訪問你

Claude Code 的官方最佳實踐裡有一招很好用：**當你還沒想清楚的時候，不要硬寫，請 AI 反過來訪問你，問到它能寫出規格為止。**

- 參考用 prompt：

```text
我想做：［一句話描述你的點子］。
請你扮演產品經理，先不要寫任何程式。
一次只問我一個問題，問到你能幫我寫出一頁規格為止。
規格要包含：問題、誰會用、要做的事、這次明確不做的事、使用流程、需要記住的資料。
問完之後，整理成 SPEC.md 給我。
```

小技巧：

- AI 問你的問題，如果你回答「都可以」，那就代表**你還沒決定**，請自己決定一個。
- AI 幫你寫好之後，**一定要自己讀一遍**，把不是你要的刪掉。規格是你的，不是 AI 的。

### 🧪 換你寫

開一個 `SPEC.md`，先把七個欄位的前六個寫完。

- 🟢 **入門路線**：用上面的 prompt 讓 AI 訪問你，再自己修改。
- 🔵 **進階路線**：自己先寫，再請 AI 「挑出這份規格裡模糊、會讓工程師猜的地方」。

## 7. 驗收條件：怎樣才算「做好了」

規格裡最容易被跳過、但最有用的就是這一欄。

> **驗收條件（Acceptance Criteria）**：一組可以判斷「對」或「錯」的句子，用來檢查功能有沒有做好。

沒有驗收條件會發生什麼事？

```text
你：功能做好了嗎？
AI：做好了！
你：（打開來看）……按鈕按了沒反應啊。
AI：抱歉！我修好了！
你：（再打開）……現在會抽到昨天吃過的店。
```

你跟 AI 對「做好」的定義不一樣。驗收條件就是把定義先講好。

### 7.1 Given / When / Then：三段式寫法

這個寫法來自「行為驅動開發（BDD）」，柏克萊大學的軟體工程課（CS169）就用它把需求寫成可以檢查的情境。

```text
Given（在什麼情況下）
When （使用者做了什麼）
Then （系統應該怎麼反應）
```

午餐輪盤的例子：

```text
情境 1：正常抽籤
Given 口袋名單裡有 5 家店，最近 3 天都沒吃過
When  我按下「抽！」
Then  畫面顯示其中一家店的名字

情境 2：避開最近吃過的
Given 口袋名單裡有 5 家店，其中「阿婆麵」是昨天吃的
When  我按下「抽！」
Then  抽到的不會是「阿婆麵」

情境 3：名單是空的
Given 口袋名單裡沒有任何店
When  我按下「抽！」
Then  畫面顯示「先新增幾家店吧！」，而不是當掉或一片空白
```

一個情境大概 3–5 句就好，太長代表你一次想測太多東西。

### 7.2 爛驗收 vs 好驗收

| ❌ 爛驗收（沒辦法判斷對錯） | ✅ 好驗收（一看就知道過沒過） |
| --- | --- |
| 介面要好看 | 在手機上打開，不用左右滑就能看到「抽！」按鈕 |
| 要很快 | 按下「抽！」後 1 秒內顯示結果 |
| 要能處理錯誤 | 名單是空的時候按「抽！」，會顯示提示文字 |
| 資料要保存 | 新增一家店後重新整理頁面，那家店還在 |

### 7.3 每個功能至少寫兩條

一條**正常情況**，一條**例外情況**。
第五課我們講過「回饋」：系統做完事要讓使用者知道，**做不到的時候更要讓使用者知道**。例外情境就是在檢查這件事。

<details>
<summary>另一種寫法：EARS（打開看看）</summary>

AWS 的 Kiro 用另一種格式寫需求，叫做 EARS（Easy Approach to Requirements Syntax）。最常用的句型長這樣：

```text
當［某件事發生］時，系統應該［做出某個反應］。
```

例如：

```text
當使用者按下「抽！」且名單為空時，系統應該顯示「先新增幾家店吧！」。
當使用者新增店家時，系統應該把店家存起來，重新整理後仍然存在。
```

跟 Given/When/Then 一樣的精神：**把「應該怎樣」寫成可以檢查的句子**。挑一種你順手的就好。

</details>

<details>
<summary>驗收條件 → 自動測試（打開看看）</summary>

第五課最後我們請 AI 寫過測試腳本。有了驗收條件，你可以直接請 AI 把它們變成自動測試：

```text
請根據 SPEC.md 裡的驗收條件，為每一條寫一個自動測試。
測試名稱請用驗收條件的情境名稱。
先列出你打算寫的測試清單給我確認，不要直接寫。
```

之後每次 AI 改完程式，跑一次測試就知道有沒有把舊功能弄壞。這就是第五課講的「回歸測試」。

</details>

把你 `SPEC.md` 的第 7 欄補上：每個核心功能各寫 **1 條正常 + 1 條例外**。

## 8. 做不做得出來？先戳一下

規格寫好了，代表你知道「要做什麼」。但還有一個問題：**你做得出來嗎？**

### 8.1 先問懂的人，但要問對問題

專案裡那些太未知、太複雜、掉進去不知道要多久才爬得出來的部分，《Shape Up》叫它們**兔子洞（Rabbit Hole）**。很多專案超時，不是每件事都慢一點，而是某一兩個兔子洞慢了好幾倍。

想找出兔子洞，可以問身邊技術比較強的朋友（或問 AI），但問法很重要：

```text
❌ 「X 做得到嗎？」→ 答案幾乎都是「做得到」（什麼都做得到，只是要多久）
✅ 「X 能在 2 週內，以我的程度做完嗎？」→ 這才是你要的答案
```

- 參考用 prompt：

```text
我是［程度：例如只會用 AI 寫簡單程式］，大概有［X 小時］可以做這個作品。
這是我的元素清單：［貼上］。
請不要寫程式。幫我找出：
1. 哪些部分以我的程度，可能會花超過預期很多的時間（兔子洞）；
2. 每個兔子洞，有沒有一個更簡單、確定做得到的替代方案；
3. 如果要在這個時間內做完，你建議砍掉什麼。
```

### 8.2 行走的骨架

在動手之前，先認識你第一個要做出來的東西。

你的 Good 那一層，如果能做成一個從頭到尾都能跑的版本，它有個名字：

> **Walking Skeleton（行走的骨架）**：系統最小、最薄的版本，但能**從頭到尾完成一件事**。

這個詞是敏捷開發先驅 Alistair Cockburn 提出的。骨架沒有肉、沒有皮，很醜，但**它會走路**。之後你要做的，就是一片一片幫它長肉。

### 8.3 骨架 vs MVP

| | 行走的骨架 | MVP（最小可行產品） |
| --- | --- | --- |
| 目的 | 確認整條路是通的，技術上接得起來 | 測試使用者是不是真的需要 |
| 給誰看 | 可以只給自己或隊友看 | 給真實使用者用 |
| 大小 | 通常比 MVP 更小 | 骨架長了一點肉之後 |

骨架是 MVP 的前一步。**先確定路是通的，再確定有人要走。**

### 8.4 原型、骨架、Spike：三個容易搞混的東西

| | 原型（Prototype） | 行走的骨架 | Spike |
| --- | --- | --- | --- |
| 目的 | 讓人看看長什麼樣子 | 打通整條路 | 回答一個技術問題 |
| 做完之後 | **丟掉** | **保留**，繼續長大 | **丟掉** |
| 會真的運作嗎 | 不一定，可以是假的 | 會，在真實環境跑 | 會，但只測一件事 |
| 比喻 | 電影布景：只有門面 | 房子的鋼筋骨架 | 用一根長釘戳戳看地基硬不硬 |

《程序員修煉之道（The Pragmatic Programmer）》這本經典書，把骨架這種東西叫做 **Tracer Bullet（曳光彈）**：晚上射擊時，曳光彈會發光，讓你看到子彈實際飛到哪裡，再調整瞄準。
書裡有一個很實用的提醒：**原型是做來丟的。如果你發現自己捨不得丟，那就不要做原型了，直接做骨架。**

用 AI 寫程式的時候這點特別重要。AI 很快就能生出一個「看起來很像真的」的原型，然後你就捨不得丟，開始在上面一直加功能。但原型本來就不是為了長大而做的，加到最後就會變成一團亂。

### 8.5 Spike：先戳一下不確定的地方

在打通骨架之前，先檢查：**你的 Good 和 Better 裡，有沒有你「不知道做不做得到」的東西？**

> **Spike**：一個限時的小實驗，只為了回答**一個**技術問題。做完的程式碼丟掉，留下的是答案。

這個詞來自極限編程（Extreme Programming），由 Kent Beck 提出。

Spike 的規則：

```text
1. 只問一個問題（「X 做得到嗎？」）
2. 嚴格限時（今天課堂上：30 分鐘）
3. 做完就丟（它不是作品的一部分）
4. 寫下結論
```

結論只有三種：

| 結論 | 意思 | 下一步 |
| --- | --- | --- |
| 🟢 可行 | 做得到，而且知道怎麼做了 | 放進骨架 |
| 🟡 要調整 | 做得到，但要換個做法或縮小範圍 | 修改元素清單或規格 |
| 🔴 換路 | 以現在的能力和時間做不到 | 換一個技術，或把這個功能移到 Best、甚至不做清單 |

### 8.6 午餐輪盤的 Spike

午餐輪盤有一個關鍵問題：

```text
❓ 室友 A 在自己手機上新增了一家店，室友 B 的手機上看得到嗎？
❓ 「最近 3 天吃過」的紀錄，三個人看到的是同一份嗎？
```

這是「**多人共用資料**」的問題。如果你用最簡單的方式（把資料存在瀏覽器裡），每個人看到的都只有自己的資料，**跟室友一起用的那個 Better 就做不到了**。

這就是一個必須先 Spike 的問題：

| 試試看 | 結果 |
| --- | --- |
| 單頁 HTML + 瀏覽器儲存 | 🔴 每個人只看得到自己的，不行 |
| Google 表單 + 試算表 | 🟢 大家填同一張表單，資料都進同一個試算表 |
| Python + Streamlit + 試算表 | 🟡 可以，但要研究怎麼連 Google 試算表 |
| 用 Firebase、Supabase 這類雲端資料庫 | 🟡 可以，但要學新東西，可能要多花時間 |

看到了嗎？如果沒有先 Spike，你可能會花一整晚做一個很漂亮的 HTML 頁面，然後才發現「啊，室友看不到我的名單」。

如果結論是 🔴，也不一定要換技術。你也可以回頭改規格：把「跟室友共用」移到 Best，第一版先只給自己用。**改規格也是一種解法。**

### 🧪 換你 Spike

1. 看你的元素清單和 SPEC，列出你「不確定做不做得到」的地方。
2. 挑最不確定的那**一個**，限時 30 分鐘做實驗（可以叫 AI 幫你寫一個最小的測試程式）。
3. 寫下結論：🟢／🟡／🔴。

- 參考用 prompt：

```text
我想確認一件事：［你的技術問題，例如「多個使用者能不能看到同一份資料」］。
請幫我寫一個「最小的實驗程式」來回答這個問題：
- 不要做任何介面設計，能證明可不可行就好；
- 告訴我要怎麼執行、怎麼判斷成功或失敗；
- 這個程式之後會丟掉，不用考慮可維護性。
```

## 9. 從規格到計畫到任務

規格寫好、也知道做不做得出來了，可以叫 AI 開工了嗎？
還不行。**先讓 AI 想，不准它寫。**

```text
SPEC（做什麼） → PLAN（怎麼做） → TASKS（拆成小工作） → 一次做一個
```

### 9.1 計畫：讓 AI 提方案，你來挑

- 參考用 prompt：

```text
請讀 SPEC.md。先不要寫任何程式。
請提出兩種做法，用表格比較：
1. 用什麼工具／語言；
2. 會分成哪些模組，各負責什麼（介面／規則／資料／回饋）；
3. 資料存在哪裡；
4. 對新手來說的難度、需要安裝什麼；
5. 有沒有哪一條規格會因此做不到。
最後推薦一個，並說明理由。
```

為什麼要兩種？因為只有一種方案的時候，你沒辦法判斷它好不好。
有比較，你才有選擇權。

看計畫時問自己：

| 檢查點 | 為什麼重要 |
| --- | --- |
| 有沒有出現我規格裡「不做」的東西？ | AI 很愛偷渡功能 |
| 要裝的東西我裝得起來嗎？ | 環境設定是新手最常卡關的地方 |
| 模組切分我看得懂嗎？ | 看不懂的架構，壞了你也修不了 |
| 資料存哪裡？關掉再開還在嗎？ | 對應規格第 6 欄，也對照你的 Spike 結論 |

### 9.2 任務：小到可以單獨完成、單獨檢查

- 參考用 prompt：

```text
我選擇方案［A／B］。請根據 SPEC.md 和這個方案，把工作拆成任務清單：
- 每個任務要能單獨完成，而且做完可以用驗收條件檢查；
- 第一個任務必須是「能跑起來的最小版本」；
- 標出任務的先後順序；
- 不要加入 SPEC.md 沒有的功能。
```

拿到清單後，**你的工作是刪**。

```text
□ 有沒有任務對應不到規格？→ 刪掉
□ 有沒有任務大到一次對話做不完？→ 請 AI 再拆
□ 第一個任務做完，我能不能打開來看到東西？→ 不能就重排
```

> **AI 負責生成，你負責確認。** 規格、計畫、任務，每一步都要你點頭才往下走。

清單上的第一個任務「能跑起來的最小版本」，就是下一節要打通的**行走的骨架**。

## 10. 打通你的骨架

現在把 Good 那一層**真的做出來**。

### 10.1 選你的路線

| 路線 | 技術 | 適合 | 能不能多人共用 | 之後怎麼分享給別人 |
| --- | --- | --- | --- | --- |
| 🟢 A | Google 表單 + 試算表 | 完全不想寫程式 | ✅ | 分享表單和試算表連結 |
| 🟢 B | 單頁 HTML + 瀏覽器儲存 | 只給自己用的工具 | ❌ | GitHub Pages |
| 🟡 C | Python + Streamlit | 會一點 Python、想做資料類的作品 | 看資料存哪 | Streamlit Community Cloud |
| 🔵 D | 自選技術 + 雲端資料庫 | 技術強、想挑戰 | ✅ | 自選（Vercel、Render 等） |

**沒有哪條路線比較高級。** 能用最簡單的工具打通，就是好骨架。
一個用 Google 表單加試算表做出來、明天就能用的東西，比一個做了一半的 React App 有價值多了。

### 10.2 叫 AI 幫你打通

- 參考用 prompt：

```text
我在做：［作品一句話］。規格在 SPEC.md。
這是我元素清單裡 Good 那一層：［每個元素一句話］。
我選擇的技術是：［路線 A／B／C／D 的技術］。
Spike 的結論是：［你的結論］。

請幫我做出「行走的骨架」：
1. 每一步只用最簡單的做法，不要加任何 Good 以外的功能；
2. 不用好看，能從頭走到尾就好；
3. 先告訴我會有哪些檔案、各負責介面／規則／資料／回饋的哪一部分；
4. 我確認之後再寫程式；
5. 最後告訴我怎麼在自己電腦上執行。
```

### 10.3 骨架檢查表

做好之後，用這張表檢查：

| 檢查項目 | 通過？ |
| --- | --- |
| 我能從第一步走到最後一步，不卡住 |  |
| Good 那一層的每個元素都有做到（就算很醜） |  |
| 有碰到四個模組：介面、規則、資料、回饋 |  |
| 關掉再打開（重新整理），資料還在 |  |
| 沒有偷偷加 Good 以外的功能 |  |

最後一條很重要。AI 很熱心，常常會「順便」幫你加功能。看到就刪掉。

### 10.4 記得存檔

```shell
git add .
git commit -m "行走的骨架：從新增店家到抽籤可以走完一輪"
```

## 大總結啦

> **「第一個作品，做完比做大重要。」**

### 一：從想法到骨架的路線圖

$$\text{注意} \rightarrow \text{驗證} \rightarrow \text{範疇} \rightarrow \text{塑形} \rightarrow \text{規格} \rightarrow \text{Spike} \rightarrow \text{任務} \rightarrow \text{骨架}$$

* **注意（第 0 節）**：好點子來自你注意到的痛點，痛點日記比坐著想有用。
* **驗證（第 1–2 節）**：先找最危險的假設，用不寫 code 的方法測；練功作品就問「我自己會用嗎」。
* **範疇（第 3 節）**：Good／Better／Best，只做到 Good 也算完成；不做清單是你的除草機。
* **塑形（第 4 節）**：Breadboard 和元素清單，夠具體可以開工，夠模糊保留彈性。
* **規格（第 5–7 節）**：SPEC.md 七欄，寫 What 和 Why，不寫 How；驗收條件用 Given／When／Then。
* **Spike（第 8 節）**：問「我的程度、這點時間做得完嗎」；不確定的地方限時 30 分鐘戳一下。
* **任務（第 9 節）**：AI 提兩個方案你來挑，AI 拆任務你來刪。
* **骨架（第 10 節）**：先打通最陽春的一條路，醜但會動，再一片一片長肉。

### 二：三個「先」

* **先驗證，再寫 code**：寫 code 是最貴的驗證方式。
* **先決定不做什麼**：範疇會像草一樣長出來。
* **先讓 AI 想，不准它寫**：規格、計畫、任務，每一步都等你點頭。

### 三：給 AI 的三個煞車

* **不做清單**：沒寫「不做」，AI 就會一直做。
* **驗收條件**：把「做好」的定義先講好。
* **一次一個任務**：不讓 AI 一口氣把整個專案寫完（然後全壞）。

### 給文組同學的話

今天這堂課，有一大半其實跟寫程式無關：找出真正的痛點、檢查有沒有人要、決定不做什麼、把模糊的想法寫成別人看得懂的文件。
這些在軟體業有專門的職位在做，叫產品經理（PM），而你們整理需求、組織語言、理解人的能力，在這裡是真正的超能力。AI 時代，會寫規格的人，等於手上有一整支不會累的工程團隊。就算你最後的骨架是用 Google 表單做的，它也是一個明天就能用的作品。

### 給電資組同學的話

技術強的人有一個特別的陷阱：**因為你什麼都做得出來，所以你什麼都想做。**
今天的不做清單、Good／Better／Best 和 Spike，都是在保護你不要掉進自己挖的兔子洞。另外也想想看：你之前的 side project，有幾個是因為「技術做不出來」而放棄的？又有幾個是因為「做完沒人用（包括自己）」？技術能力讓你**能**做出任何東西，今天的方法讓你知道**該**先做什麼。

- **Walking Skeleton**、**Tracer Bullet**、**Spike**：Alistair Cockburn、《The Pragmatic Programmer》、Kent Beck
