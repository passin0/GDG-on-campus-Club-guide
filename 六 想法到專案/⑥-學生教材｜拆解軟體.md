# 第 ⑥ 堂｜拆解軟體：如何掌握一個專案

> 一個軟體不是一份很長的程式碼。  
> 你今天要學的是：拿到陌生專案時，怎麼先畫地圖，再決定要改哪裡。

## 今天的任務

你會偵查一個小型專案，追蹤其中一個功能，最後提出一個「最小可行」的新功能。

完成時，你要能留下：

- 一張專案地圖
- 一條功能路徑
- 一個不會大到失控的 MVP 改動提案

---

## 1. 軟體地圖：每個角色都在做什麼？

把軟體想成一間店：前台負責讓客人看和按；後面有人處理規則；有地方記住資料；不同小組各自負責一件事。

| 角色 | 用人話說 | 可以問什麼？ |
| --- | --- | --- |
| Frontend | 使用者看得到、按得到的畫面 | 按鈕與頁面在哪裡？ |
| Backend | 處理規則、決定結果的地方 | 送出後誰在處理？ |
| 資料 | 軟體要記得的東西 | 它要保存什麼？ |
| Module | 集中處理某件事的小區塊 | 哪個檔案專門負責它？ |
| Function | 更小、一次只做一件事的動作 | 它被誰呼叫？結果去哪？ |

> 小專案不一定有獨立 Backend 或資料庫。重要的是看懂角色，不是硬背資料夾名稱。

## 2. 陌生專案從哪裡看？

不要從第一行一路讀到最後一行。照這個順序：

```text
README → 資料夾 → 入口 → 一條功能路徑
```

### README

先找：它替誰解決什麼問題？怎麼啟動？作者有沒有提醒限制？

### 資料夾

先只看名稱、猜角色，再打開檔案找證據。檔名只是線索，不是答案。

### 入口

入口是程式開始運作，或使用者第一眼進入的地方；可能是首頁、主要畫面、啟動檔或設定檔。

### 練習 ②：專案偵查表

| 我找到的地方 | 它告訴我什麼？ | 事實還是猜測？ |

| README |  |  |
| 資料夾結構 |  |  |
| 我猜的入口 |  |  |

## 3. 只追一條功能路徑

選一個使用者動作，例如「新增一件待辦事項」。一路追到結果，不要一次理解全部。

```text
使用者按下按鈕
    ↓
畫面把資料交出去
    ↓
某個 Function 檢查或處理資料
    ↓
資料被更新／儲存
    ↓
畫面顯示新結果
```

## 4. AI 是導覽員，不是拆遷隊

第一次請 AI 幫忙時，不要立刻叫它「全部改好」。先請它帶你看地圖。

```text
這是一個我不熟悉的小型專案。請不要修改程式。
請根據 README 與檔案結構，用表格說明：
1. 每個主要檔案或資料夾可能負責什麼；
2. 專案入口可能在哪裡；
3. 若我想理解［某功能］，建議依什麼順序閱讀。
不確定的地方請標記為猜測。
```

AI 給的是地圖草稿；你仍要回到檔案與畫面，確認它有沒有指對方向。

## 5. 新功能先做 MVP

MVP 的意思是：先讓最重要、最小的一版能用。

想做「待辦事項分類」時，不要一次做分類、顏色、篩選、排序、統計和分享。先做到：

> 新增一件事時能選分類，而且清單上看得到分類名稱。
