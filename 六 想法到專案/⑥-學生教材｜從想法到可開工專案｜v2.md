# 第 ⑥ 堂｜拆解軟體：從想法到可開工專案

> 「我想做一個 App」是一個很好的起點，卻還不是一個可以交給 AI 的任務。  
> 今天要練習把模糊想法，拆成第一個能開工、能驗收的功能。

## 今天要完成什麼？

你會選一個自己真的想做、或以「社團活動報名工具」為例，完成一份專案起步包：

1. 問題、目標使用者與核心流程；
2. MVP 與明確的非目標；
3. 第一個功能切片、任務順序與驗收條件；
4. 一段請 AI 協助規劃專案的 Prompt；
5. 一張初步專案地圖。

今天的 AI 角色不是自動生出完整 App，而是**需求訪談者、方案比較者與計畫審查者**。

---

## 1. 不要從「幫我做一個完整 App」開始

這種 Prompt 很常見：

```text
幫我做一個有登入、活動管理、報名、通知、付款和聊天室的社團 App。
```

它不是不能做，而是範圍太大。你很難判斷 AI 漏了什麼，也不知道第一個壞掉的地方該從哪修。

先把想法壓成一句問題：

> ［哪一種人］在［什麼情境］下，因為［什麼困難］，需要［什麼幫助］。

### 例子

> 社團社員在活動資訊分散於不同群組時，不容易知道自己報名了哪些活動，因此需要一個能查看與報名活動的工具。

### 練習 ①：我的問題一句話

＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿

---

## 2. 先畫核心使用流程

軟體不是功能清單，而是一連串使用者行動。

活動報名工具最小的流程可能是：

```text
看見活動
→ 點進活動頁
→ 按下報名
→ 看見成功或失敗結果
```

### 練習 ②：我的核心流程

| 步驟 | 使用者做什麼？ | 系統應做什麼？ | 使用者最後看見什麼？ |
| --- | --- | --- | --- |
| 1 |  |  |  |
| 2 |  |  |  |
| 3 |  |  |  |
| 4 |  |  |  |

> 如果無法在四步內說清楚，先選其中一條流程，而不是把所有功能都塞進第一版。

---

## 3. MVP：選擇現在不做什麼

MVP 不是隨便做一個陽春版本，而是用最少的功能驗證最重要的使用價值。

| 例：活動工具 | 第一版做 | 第一版不做 |
| --- | --- | --- |
| 活動資訊 | 顯示活動名稱、時間、名額 | 搜尋、分類、推薦 |
| 報名 | 可以送出一筆報名 | 登入、付款、通知 |
| 回饋 | 顯示成功或額滿 | 自動寄信、行事曆同步 |

### 練習 ③：我的範圍卡

使用者最重要的價值：＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿

MVP 必須有：＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿

這次明確不做：＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿

如果只剩 30 分鐘，我仍要完成：＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿

---

## 4. 切出第一個可交付功能

第一個功能切片應該是「使用者能完成一件事」，而不是「先做一個按鈕」或「先建資料庫」。

```text
不夠完整：做報名按鈕
可交付切片：使用者能對一場活動送出報名，並看見成功結果
```

### 練習 ④：功能切片與驗收

我的第一個功能切片：＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿

使用者完成後會看見：＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿

| 驗收案例 | 我預期的結果 |
| --- | --- |
| 正常使用 |  |
| 一個例外情況 |  |
| 舊功能不能被破壞的地方 |  |

## 5. 從功能切片拆成可做的任務

功能不等於一個任務。以「可以報名活動」為例：

```text
先決定報名需要哪些資料
→ 顯示活動與報名入口
→ 建立報名規則
→ 儲存或更新報名資料
→ 顯示成功／失敗回饋
→ 測試正常與例外情況
```

### 練習 ⑤：我的任務與順序

| 任務 | 為什麼需要它？ | 要先完成什麼？ | 完成的證據是什麼？ |
| --- | --- | --- | --- |
|  |  |  |  |
|  |  |  |  |
|  |  |  |  |
|  |  |  |  |

> 專案管理的最小版本不是排滿行程表；而是知道：**先做什麼、暫時不做什麼、什麼叫做完成。**

---

## 6. 請 AI 幫你規劃，而不是替你猜

```text
我想做的問題是：［問題一句話］。
目標使用者是：［誰］。
核心流程是：［貼上流程］。
第一版 MVP 包含：［內容］；這次不做：［內容］。
第一個功能切片是：［內容］，驗收條件是：［內容］。

請先不要產生完整程式。請幫我：
1. 檢查 MVP 是否仍然太大；
2. 提出第一個功能切片的任務順序與依賴；
3. 提出簡單專案結構，並說明每個區塊的責任；
4. 列出可能的風險與我現在不必處理的事；
5. 標示哪些地方是你的假設。
```

AI 的計畫是草稿。你要檢查：它有沒有偷塞你說過「這次不做」的功能？任務順序是否合理？每個區塊是否都有明確責任？

---

## 7. 第一張專案地圖

AI 或範例專案出現後，不必一次讀懂全部 Code。先找每個區塊負責什麼。

| 我看到的檔案／資料夾／區塊 | 它可能負責什麼？ | 它和第一個功能切片的關係 | 事實或猜測？ |
| --- | --- | --- | --- |
|  |  |  |  |
|  |  |  |  |
|  |  |  |  |

你在第⑤堂練過的「介面、規則、資料、回饋」正是這張地圖的第一批路標。

## 今天帶走的工作流

```text
一個真實問題
→ 一位目標使用者
→ 一條核心流程
→ 一個有邊界的 MVP
→ 第一個可驗收功能
→ 任務順序與風險
→ AI 協助規劃
→ 看懂初步專案結構
```

你不需要等到「想法完全成熟」才開始；但不要讓 AI 用一大坨程式替你掩蓋還沒想清楚的問題。
