## 今天的任務

下課時你會有：

```text
✅ 一張你作品的故事地圖
✅ 一條「行走的骨架」：最醜、最陽春，但從頭到尾都能跑
✅ 一個上線的網址
✅ 一份「下一刀」的 Issue 清單
```

而且你能：

- 說出為什麼「一層一層做」比「一片一片做」危險；
- 把一個大功能切成很多很薄、每一片都能用的小切片；
- 分辨原型（Prototype）、骨架（Walking Skeleton）和 Spike 的差別；
- 在一堂課內，把作品從零打通到上線。

今天的貫穿範例是：**「社團器材借用登記」**。
（社團的延長線、投影機、轉接頭，永遠不知道被誰借走了。）

## 0. 那個超漂亮的登入頁

你有沒有這種經驗：

```text
第 1 天：先做登入頁！設計得超漂亮，有漸層、有動畫。
第 2 天：再做註冊頁！也很漂亮。
第 3 天：做首頁，排版排了一整晚。
第 4 天：好，來做主要功能……資料要存哪裡？
第 5 天：研究資料庫，好難。
第 6 天：發現登入要跟資料庫接，前面的登入頁要改。
第 14 天：……
```

兩週過去了，你有三個很漂亮的頁面，但**沒有一個功能是真的能用的**。

問題出在哪？你是**一層一層**做的：先把畫面全做完，再做資料，最後才接起來。
一直到最後一刻，你都不知道整個東西能不能動。

今天要學的是另一種做法：**先做一個醜到不行、但從頭到尾都能跑的版本**，然後再一點一點變好。

> **醜的但會動，勝過漂亮但只有一半。**

## 1. 橫切 vs 直切：吃蛋糕的正確方法

想像你的作品是一個三層蛋糕：

```text
┌─────────────────────────┐
│     介面（畫面、按鈕）     │  ← 上層
├─────────────────────────┤
│     規則（判斷、計算）     │  ← 中層
├─────────────────────────┤
│     資料（儲存、讀取）     │  ← 下層
└─────────────────────────┘
```

### 1.1 橫切：一層一層吃

```text
第 1 週：把所有畫面做完    ████████████  介面
第 2 週：把所有規則做完    ████████████  規則
第 3 週：把資料庫做完      ████████████  資料
第 4 週：串起來……爆炸 💥
```

橫切的問題：**一直到最後一週，使用者都沒辦法用任何東西。** 而且你要到最後才會發現，三層根本接不起來。

### 1.2 直切：一口吃到三層

```text
切片 1   切片 2   切片 3
  ██       ██       ██     介面
  ██       ██       ██     規則
  ██       ██       ██     資料
  ↓        ↓        ↓
 能用！   更好用！  更更好用！
```

直切的每一片，都**同時碰到三層**：一點點畫面、一點點規則、一點點資料。
每切完一片，就有一個能用的東西。

> 「蛋糕比喻」是敏捷開發圈非常有名的比喻，最早由 Bill Wake 在 2003 年提出。後來幾乎每一篇講切片的文章都會用到蛋糕，已經變成業界的梗了。

### 1.3 跟第五課的連結

還記得第五課的四個模組嗎？

| 模組 | 在蛋糕裡 |
| --- | --- |
| 介面 | 上層：使用者看到、操作的部分 |
| 規則 | 中層：判斷能不能做、怎麼算 |
| 資料 | 下層：記住東西 |
| 回饋 | 從下層回到上層：告訴使用者結果 |

**每一個直切的切片，都要走完這四個模組一圈。** 這就是為什麼它「能用」。

## 2. 暖身：切大象生魚片

在切你自己的作品之前，先來玩一個練習。

這個練習叫 **Elephant Carpaccio（大象生魚片）**，由敏捷開發先驅 Alistair Cockburn 發明，後來 Henrik Kniberg 寫了一份詳細的帶領指南，世界各地的軟體團隊都拿它來練習切片。名字的意思是：**大象很大，但你可以把它切成像生魚片一樣薄。**

我們把它改成台灣版：

### 2.1 題目：手搖飲團購計算機

```text
輸入：杯數、單價、外送區域
輸出：最後要付多少錢
```

規則：

```text
外送運費（店家規定，一定要收）：
  自取 $0、三峽 $30、樹林 $50、鶯歌 $50、土城 $60、板橋 $80

團購折扣（促銷活動）：
  滿 $500 打 95 折
  滿 $1000 打 9 折
  滿 $2000 打 85 折
  滿 $3000 打 8 折
  滿 $5000 打 75 折
  ※ 折扣只算飲料，運費不打折
```

### 2.2 切片規則

先**闔上電腦**，兩三人一組，在紙上把這個計算機切成越多片越好。
每一片都必須符合：

| 規則 | 意思 |
| --- | --- |
| ✅ 有輸入、有輸出 | 使用者可以輸入東西，看到結果 |
| ✅ 能 demo | 做完可以給別人看，而且跟上一片**看得出差別** |
| ✅ 比上一片更有價值 | 使用者能多做一件事，或更正確 |
| ✅ 很小 | 大概 2–6 分鐘就能做完（如果是叫 AI 做，就是一個很短的 prompt） |
| ❌ 不能只是 | 「畫面設計」「建資料結構」「寫測試」這種使用者用不到的東西 |

**目標：至少切 10 片。** 能切到 15 片以上，你就很厲害了。

### 2.3 一個切法參考

先自己切完再看喔！

<details>
<summary>參考切法（打開看看）</summary>

```text
切片 1：輸入杯數、單價 → 顯示小計（沒運費、沒折扣）
切片 2：寫死「三峽」，小計 + $30
        → 這時候其實已經可以在三峽開始接單了！
切片 3：運費改成直接輸入金額（還不用選區域）
切片 4：可以選「三峽」或「樹林」，其他區域顯示「不外送」
切片 5：一次加入其他所有區域
        → 一個一個加沒有額外價值，一次加完就好
切片 6：寫死一個折扣：滿 $1000 打 9 折
切片 7：加入滿 $500 打 95 折
切片 8：加入剩下所有折扣
切片 9：輸入檢查：杯數是 0 或負數時，顯示錯誤訊息
切片 10：顯示明細（小計、折扣、運費、總計各一行）
切片 11：好看一點的介面
```

注意幾件事：

1. **第一片超級小**。小到有點蠢，但它從頭到尾都能跑。
2. **運費比折扣先做**。因為運費是「一定要收」的，折扣是「促銷」的。少了折扣店家還能營業，少了運費就是虧錢。**先做最有價值的，不是先做最有趣的。**
3. **介面放最後**。漂亮的畫面很重要，但不是最重要的。
4. **輸入檢查放後面**。先讓正常情況能跑，再處理例外。

</details>

### 2.4 🔵 進階：真的寫出來

會寫程式（或很會用 AI）的組別，打開電腦：

```text
- 每 8 分鐘一輪，一共 5 輪
- 每做完一片，喊一聲「切！」
- 每輪結束，把成果 demo 給隔壁組看（10 秒就好，時間繼續跑）
```

### 2.5 驗收時間

全部組別用同一組輸入跑一次你們的計算機：

```text
杯數：37 杯
單價：$65
區域：樹林
```

大家的答案一樣嗎？

<details>
<summary>答案與討論（打開看看）</summary>

```text
小計：37 × 65 = $2,405
滿 $2000，打 85 折：2,405 × 0.85 = $2,044.25
運費：樹林 $50
總計：$2,094.25 → ？？？
```

很多組會在這裡吵起來：

- 小數點要四捨五入、無條件捨去，還是無條件進位？
- 是先加運費再判斷折扣門檻，還是先算折扣？
- 有人把運費也打折了

**題目沒講清楚的地方，每個人都做了不同的假設。** 在真實的專案裡，這些假設通常要到使用者抱怨「為什麼我被多收了 1 塊錢」的時候才會被發現。

這就是為什麼「每片都要能 demo、要能驗收」：越早讓別人用，越早發現你偷偷做了什麼假設。

</details>

### 2.6 回顧

```text
1. 你們組切了幾片？第一片有多小？
2. 你們是先做運費還是先做折扣？為什麼？
3. （有寫程式的組）你對你的程式碼有多驕傲？1 到 5 分。
```

第 3 題通常會得到很低的分數。趕著切片的時候，很容易寫出很亂的程式。
**切得薄不代表可以寫得爛。** 這點我們第 8 節再回來談。

## 3. 故事地圖：把你的作品攤開

暖身完畢，換你自己的作品。
第一步是把它**攤開**，用的工具叫 **User Story Map（使用者故事地圖）**，由 Jeff Patton 提出，2014 年寫成同名的書。

### 3.1 故事地圖長什麼樣子？

```text
橫軸：使用者照順序做的事（骨幹）
───────────────────────────────────────────────────→

 看器材清單     登記借用       查誰借走       歸還器材
 ──────────    ──────────    ──────────    ──────────
 顯示所有器材   輸入名字       清單顯示       按「歸還」      ← 最重要
               選器材         「借出中：誰」

 顯示借出狀態   選借用日期     顯示借了幾天   記錄歸還時間     ← 次重要
               預計歸還日

 依類別分類     借用規則提醒   逾期標紅色     歸還時拍照       ← 有的話很好
 搜尋                         LINE 通知                      

縱軸：由上到下，越來越不重要 ↓
```

### 3.2 一步一步畫

**Step 1：寫骨幹（橫軸）**
用「動詞開頭」寫出使用者從開始到結束會做的事，照順序由左到右排。4–7 個就夠了。

```text
看器材清單 → 登記借用 → 查誰借走 → 歸還器材
```

**Step 2：每個步驟下面，寫具體的做法**
用便利貼或表格，在每個步驟下面寫出具體要做的事。想到什麼都寫，先不要管能不能做。

**Step 3：由上到下排優先順序**
每一欄裡，最重要、最基本的放最上面，越往下越「有的話很好」。

**Step 4：畫線**
在最上面那一排的下面，畫一條橫線。

```text
 看器材清單     登記借用       查誰借走       歸還器材
 顯示所有器材   輸入名字+選器材  顯示借出中:誰   按「歸還」
═══════════════════════════════════════════════════  ← 第一條線
```

**線上面那一排，就是你今天要打通的東西。**

### 🧪 換你畫

畫出你作品的故事地圖，並畫出第一條線。

- 🟢 **入門路線**：用下面的 prompt 請 AI 幫你起個頭，再自己調整。
- 🔵 **進階路線**：自己畫，再請 AI 挑戰你「第一條線上的東西還能不能更少」。

- 參考用 prompt：

```text
我想做：［你的作品一句話］。
請幫我畫一張使用者故事地圖（用表格）：
1. 第一列是骨幹：使用者照順序做的 4–7 件事，用動詞開頭；
2. 每一欄下面列出具體做法，由上到下越來越不重要；
3. 標出第一列，就是「能從頭走到尾的最簡單版本」。
先不要寫程式。
```

## 4. 行走的骨架

第一條線上面那一排，有個名字：

> **Walking Skeleton（行走的骨架）**：系統最小、最薄的版本，但能**從頭到尾完成一件事**。

這個詞是 Alistair Cockburn（對，就是發明大象生魚片的那位）提出的。骨架沒有肉、沒有皮，很醜，但**它會走路**。之後你要做的，就是一片一片幫它長肉。

### 4.1 骨架 vs MVP

| | 行走的骨架 | MVP（最小可行產品） |
| --- | --- | --- |
| 目的 | 確認整條路是通的，技術上接得起來 | 測試使用者是不是真的需要 |
| 給誰看 | 可以只給自己或隊友看 | 給真實使用者用 |
| 大小 | 通常比 MVP 更小 | 骨架長了一點肉之後 |

骨架是 MVP 的前一步。**先確定路是通的，再確定有人要走。**

### 4.2 原型、骨架、Spike：三個容易搞混的東西

| | 原型（Prototype） | 行走的骨架 | Spike |
| --- | --- | --- | --- |
| 目的 | 讓人看看長什麼樣子 | 打通整條路 | 回答一個技術問題 |
| 做完之後 | **丟掉** | **保留**，繼續長大 | **丟掉** |
| 會真的運作嗎 | 不一定，可以是假的 | 會，在真實環境跑 | 會，但只測一件事 |
| 比喻 | 電影布景：只有門面 | 房子的鋼筋骨架 | 用一根長釘戳戳看地基硬不硬 |

《程序員修煉之道（The Pragmatic Programmer）》這本經典書，把骨架這種東西叫做 **Tracer Bullet（曳光彈）**：晚上射擊時，曳光彈會發光，讓你看到子彈實際飛到哪裡，再調整瞄準。
書裡有一個很實用的提醒：**原型是做來丟的。如果你發現自己捨不得丟，那就不要做原型了，直接做骨架。**

用 AI 寫程式的時候這點特別重要。AI 很快就能生出一個「看起來很像真的」的原型，然後你就捨不得丟，開始在上面一直加功能。但原型本來就不是為了長大而做的，加到最後就會變成一團亂。

## 5. Spike：先戳一下不確定的地方

在打通骨架之前，先檢查：**第一條線上，有沒有你「不知道做不做得到」的東西？**

### 5.1 什麼是 Spike？

> **Spike**：一個限時的小實驗，只為了回答**一個**技術問題。做完的程式碼丟掉，留下的是答案。

這個詞來自極限編程（Extreme Programming），由 Kent Beck 提出。

### 5.2 Spike 的規則

```text
1. 只問一個問題（「X 做得到嗎？」）
2. 嚴格限時（今天課堂上：30 分鐘）
3. 做完就丟（它不是作品的一部分）
4. 寫下結論
```

結論只有三種：

| 結論 | 意思 | 下一步 |
| --- | --- | --- |
| 🟢 可行 | 做得到，而且知道怎麼做了 | 放進骨架 |
| 🟡 要調整 | 做得到，但要換個做法或縮小範圍 | 修改故事地圖 |
| 🔴 換路 | 以現在的能力和時間做不到 | 換一個技術，或把這個功能移到線下面 |

### 5.3 器材借用的 Spike

器材借用登記有一個關鍵問題：

```text
❓ 社員 A 在自己手機上登記借了投影機，社員 B 在他的手機上看得到嗎？
```

這是「**多人共用資料**」的問題。如果你用最簡單的方式（把資料存在瀏覽器裡），每個人看到的都只有自己的資料，**整個器材借用系統就沒有意義了**。

這就是一個必須先 Spike 的問題：

| 試試看 | 結果 |
| --- | --- |
| 單頁 HTML + 瀏覽器儲存 | 🔴 每個人只看得到自己的，不行 |
| Google 表單 + 試算表 | 🟢 大家填同一張表單，資料都進同一個試算表 |
| Python + Streamlit + 試算表 | 🟡 可以，但要研究怎麼連 Google 試算表 |
| 用 Firebase、Supabase 這類雲端資料庫 | 🟡 可以，但要學新東西，可能要多花時間 |

看到了嗎？如果沒有先 Spike，你可能會花一整晚做一個很漂亮的 HTML 頁面，然後才發現「啊，大家看不到彼此的資料」。

### 🧪 換你 Spike

1. 看你的第一條線，列出你「不確定做不做得到」的地方。
2. 挑最不確定的那**一個**，限時 30 分鐘做實驗（可以叫 AI 幫你寫一個最小的測試程式）。
3. 寫下結論：🟢／🟡／🔴。

- 參考用 prompt：

```text
我想確認一件事：［你的技術問題，例如「多個使用者能不能看到同一份資料」］。
請幫我寫一個「最小的實驗程式」來回答這個問題：
- 不要做任何介面設計，能證明可不可行就好；
- 告訴我要怎麼執行、怎麼判斷成功或失敗；
- 這個程式之後會丟掉，不用考慮可維護性。
```

## 6. 打通你的骨架

Spike 結束，你知道路是通的了。現在把第一條線上的東西**真的做出來**。

### 6.1 選你的路線

| 路線 | 技術 | 適合 | 能不能多人共用 | 上線方式 |
| --- | --- | --- | --- | --- |
| 🟢 A | Google 表單 + 試算表 | 完全不想寫程式 | ✅ | 分享表單和試算表連結 |
| 🟢 B | 單頁 HTML + 瀏覽器儲存 | 只給自己用的工具 | ❌ | GitHub Pages |
| 🟡 C | Python + Streamlit | 會一點 Python、想做資料類的作品 | 看資料存哪 | Streamlit Community Cloud |
| 🔵 D | 自選技術 + 雲端資料庫 | 技術強、想挑戰 | ✅ | 自選（Vercel、Render 等） |

**沒有哪條路線比較高級。** 能用最簡單的工具打通，就是好骨架。
Google 表單加試算表做出來的器材借用系統，社團明天就能用，比一個做了一半的 React App 有價值多了。

### 6.2 叫 AI 幫你打通

- 參考用 prompt：

```text
我在做：［作品一句話］。
這是我故事地圖的第一條線：［步驟 1 → 2 → 3 → 4，每步一句話］。
我選擇的技術是：［路線 A／B／C／D 的技術］。
Spike 的結論是：［你的結論］。

請幫我做出「行走的骨架」：
1. 每一步只用最簡單的做法，不要加任何第一條線以外的功能；
2. 不用好看，能從頭走到尾就好；
3. 先告訴我會有哪些檔案、各負責介面／規則／資料／回饋的哪一部分；
4. 我確認之後再寫程式；
5. 最後告訴我怎麼在自己電腦上執行。
```

### 6.3 骨架檢查表

做好之後，用這張表檢查：

| 檢查項目 | 通過？ |
| --- | --- |
| 我能從第一步走到最後一步，不卡住 |  |
| 第一條線上的每一步都有做到（就算很醜） |  |
| 有碰到四個模組：介面、規則、資料、回饋 |  |
| 關掉再打開（重新整理），資料還在 |  |
| 沒有偷偷加第一條線以外的功能 |  |

最後一條很重要。AI 很熱心，常常會「順便」幫你加功能。看到就刪掉。

## 7. 上線：拿到一個網址

**只在你自己電腦上能跑的作品，不算完成。**
能傳一個網址給朋友，讓他在自己的手機上打開，才算。

### 7.1 🟢 路線 B：GitHub Pages（單頁 HTML）

```text
1. 在 GitHub 開一個 repo，把 index.html 上傳上去
2. 進入 repo 的 Settings → 左邊選 Pages
3. Source 選「Deploy from a branch」
4. Branch 選 main，資料夾選 /(root)，按 Save
5. 等一兩分鐘，重新整理，上面會出現你的網址：
   https://你的帳號.github.io/repo名稱/
```

### 7.2 🟡 路線 C：Streamlit Community Cloud（Python）

```text
1. 把程式碼（例如 app.py）和 requirements.txt 上傳到 GitHub
2. 到 Streamlit Community Cloud 用 GitHub 帳號登入
3. 選「Create app」，選你的 repo、分支、主程式檔案
4. 按 Deploy，等它安裝完成
5. 之後每次 push 到 GitHub，網站會自動更新
```

小提醒：公開的 app 是免費的；一段時間沒人用會進入休眠，下次打開要等它醒來。

### 7.3 🟢 路線 A：Google 表單 + 試算表

```text
1. 表單右上角「傳送」→ 複製連結 → 這就是「登記借用」的網址
2. 試算表右上角「共用」→ 設定成「知道連結的人可以檢視」→ 這就是「查誰借走」的網址
3. 把兩個連結放在社團群組的記事本
```

恭喜，你的器材借用系統上線了。

### 7.4 上線檢查

```text
□ 用「別人的」手機打開網址，能用嗎？
□ 用手機的無痕模式打開，能用嗎？
□ 把網址傳給一個朋友，他不用你解釋就知道怎麼用嗎？
```

如果第三點不行，那就是你的**下一刀**。

## 8. 下一刀切哪裡

骨架會走路了。接下來就是一刀一刀幫它長肉。

### 8.1 回到故事地圖，畫第二條線

```text
 看器材清單     登記借用        查誰借走        歸還器材
 顯示所有器材   輸入名字+選器材   顯示借出中:誰    按「歸還」
═══════════════════════════════════════════════════  ← 骨架（完成 ✅）
 顯示借出狀態   選借用日期       顯示借了幾天     記錄歸還時間
               預計歸還日
═══════════════════════════════════════════════════  ← 第二條線（下一版）
 依類別分類     借用規則提醒     逾期標紅色       歸還時拍照
```

**每一版都要能從頭走到尾**，只是每一步多了一點東西。這就是直切。

### 8.2 每一刀變成一張 Issue

把第二條線上的每一格，開成一張 GitHub Issue：

```markdown
標題：登記借用時可以選「預計歸還日」

## 使用者可以做到
登記借用時選擇預計歸還日期，清單上會顯示。

## 怎樣算做好
- 登記時沒選日期，預設為 7 天後
- 清單上看得到每件器材的預計歸還日

## 這張不做
逾期提醒（下一版再做）。
```

### 8.3 好切片的三個問題

切下一刀之前，問自己：

| 問題 | 為什麼 |
| --- | --- |
| 這一片做完，使用者能多做一件事嗎？ | 不能的話，它可能只是「橫切」的一層 |
| 這一片能單獨做完、單獨驗收嗎？ | 要等別的片做完才能用，代表切錯了 |
| 這一片夠小嗎？一次跟 AI 的對話能做完嗎？ | 做不完就再切 |

<details>
<summary>業界版：INVEST 原則（打開看看）</summary>

上面三個問題是從一個叫 **INVEST** 的原則簡化來的，由 Bill Wake（就是提出蛋糕比喻的那位）整理，用來判斷一個「使用者故事」切得好不好：

| 字母 | 意思 | 白話 |
| --- | --- | --- |
| **I**ndependent | 獨立 | 不用等別的片做完 |
| **N**egotiable | 可協商 | 細節可以討論調整 |
| **V**aluable | 有價值 | 使用者感受得到 |
| **E**stimable | 可估計 | 大概知道要花多久 |
| **S**mall | 夠小 | 很快能做完 |
| **T**estable | 可測試 | 知道怎樣算做好 |

切片切得不好，最常見的就是違反 V（只是技術層，使用者感受不到）和 S（太大）。

</details>

### 8.4 切得薄，不代表可以寫得爛

還記得大象生魚片的回顧問題嗎？「你對你的程式碼有多驕傲？」

在帶這個練習的經驗分享裡，常有人發現：**趕著切片的時候，大家都沒寫測試，幾輪之後就開始不安。** 他們的結論是：第一個切片除了功能，還應該順便把這些基本功建立起來：

```text
骨架的「完成定義」：
□ 有一個 repo，有版本紀錄
□ README 寫了「這是什麼、怎麼打開」
□ 有一份驗收清單（或幾個自動測試），每次改完都跑一遍
□ 能在別人的裝置上打開
```

這些東西在骨架階段做，只要幾分鐘。等作品長大了才補，會痛很多倍。

- 參考用 prompt：

```text
這是我目前的骨架程式。請幫我：
1. 寫一份 README，包含：這是什麼、怎麼打開、目前做到哪；
2. 根據目前的功能，列出一份驗收清單（每個功能一條正常、一條例外）；
3. 如果適合，幫我寫 1–3 個最基本的自動測試，並告訴我怎麼執行。
不要修改任何現有功能。
```

## 大總結啦

> **「先讓它從頭跑到尾，再讓它變好。」**

### 一：直切，不要橫切

* **橫切**：一層一層做完再接起來 → 最後才知道能不能動。
* **直切**：每一片都碰到介面、規則、資料、回饋 → 每一片都能用。
* **大象生魚片**：再大的東西都能切得很薄，第一片要小到有點蠢。
* **先做最有價值的**，不是先做最有趣的。

### 二：從地圖到骨架到上線

$$\text{故事地圖} \rightarrow \text{第一條線} \rightarrow \text{Spike} \rightarrow \text{骨架} \rightarrow \text{上線} \rightarrow \text{下一刀}$$

* **故事地圖**：橫軸是使用者的步驟，縱軸由上到下越來越不重要。
* **第一條線**：每一欄只留最上面那張，就是骨架。
* **Spike**：限時 30 分鐘，只回答一個問題，做完就丟。
* **骨架**：醜，但會走路。之後一片一片長肉。
* **上線**：能傳網址給朋友，才算完成。

### 三：三個容易搞混的東西

* **原型**：做來看的，用完就丟。捨不得丟，就改做骨架。
* **骨架**：做來長大的，要在真實環境跑。
* **Spike**：做來回答問題的，答案留下，程式碼丟掉。

### 給文組同學的話

今天你可能是用 Google 表單和試算表完成骨架的，然後看到旁邊的同學在寫 Python，覺得自己的比較「不像程式」。
完全不用這樣想。**你做出了一個明天社團就能用的系統**，而且你學會了軟體工程裡最重要的思考方式之一：先打通、再變好。很多工程師花了好幾年才學會不要先做漂亮的登入頁。等你哪天想換成真正的程式，故事地圖和切片的方法一模一樣，只是工具換了而已。

### 給電資組同學的話

今天的大象生魚片，你可能覺得「這麼簡單的計算機，我五分鐘就寫完了，幹嘛切 15 片」。
重點不在這個計算機，在**切的能力**。當你之後做的是一個要好幾週的專案，能不能把它切成每天都能 demo 的小片，就是你能不能做完的關鍵。另外，驗收時你們組的答案跟別組一樣嗎？如果不一樣，你寫程式的時候，是不是也偷偷做了題目沒講的假設？
