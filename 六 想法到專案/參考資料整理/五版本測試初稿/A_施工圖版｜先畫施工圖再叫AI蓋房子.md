> AI 讓「寫出程式」變便宜了；「講清楚要寫什麼」反而變貴了。

上一堂課，我們學會當「監工」：看懂別人蓋好的房子，知道哪裡漏水該找誰修。
這一堂課要換你自己蓋房子。

但你應該有過這種經驗：

```text
你：幫我做一個記帳 App。
AI：好的！（噼哩啪啦 300 行）
你：……這不是我要的。
AI：抱歉！我重新寫一個！（又 300 行）
你：……這更不是。
```

不是 AI 笨，是你只給了它一句話，剩下的 99% 都是它自己腦補的。
今天我們要學的，就是在叫 AI 動工之前，先畫一份 **施工圖**。

##### 出發前小提醒：今天不會教你任何「神級 prompt」。你會帶走的是一套「把想法變成規格」的方法，不管你用 ChatGPT、Gemini、Claude Code、Cursor 還是 Antigravity 都通用。

## 今天的任務

下課時，你的 GitHub 上會有一個屬於你的專案 repo，裡面有：

```text
my-project/
├── README.md     ← 給人看的：這是什麼、怎麼用
├── SPEC.md       ← 給你和 AI 看的：要做什麼、不做什麼、怎樣算做好
└── Issues        ← 一張一張的工作單，一次給 AI 一張
```

而且你能：

- 用一頁文件講清楚：你要做什麼、**不做什麼**；
- 幫每個功能寫出「怎樣算做好」的驗收條件；
- 讓 AI 先問你問題、先列計畫，而不是直接開寫；
- 把一個專案拆成一次只給 AI 一個的小任務。

今天的貫穿範例是：**「三峽午餐輪盤」**——一個幫你決定午餐吃什麼的小工具。
（北大人每天中午都要面對的人生難題。）

## 0. 同一句話，三個 App

先來做個實驗。把這句話丟給 AI 三次（記得每次都開新對話）：

```text
幫我做一個決定午餐吃什麼的 App。
```

你可能會拿到這三種完全不同的東西：

| | 第一次 | 第二次 | 第三次 |
| --- | --- | --- | --- |
| 長相 | 一個轉盤，按下去隨機轉 | 一個有登入、評分、留言的餐廳平台 | 先問你今天心情、預算，再推薦 |
| 資料 | 寫死 5 家店 | 要你接 Google Maps API | 一個很長的問卷 |
| 你的反應 | 太陽春了吧 | 我只是想決定午餐…… | 好像不錯，但我沒說要問卷 |

三個都「能動」，三個都不是你要的。

為什麼？因為你腦中其實有很多沒說出口的決定：

```text
- 店家清單是我自己輸入，還是 AI 去抓？
- 要不要記得我上次吃過什麼，避免連續吃同一家？
- 只有我自己用，還是要跟室友一起投票？
- 手機用還是電腦用？
```

你沒講，AI 就只能猜。而每一次猜的都不一樣。

> **Generate ≠ What I want.** AI 生出來的東西，會「長得像」你要的，但不一定「是」你要的。

GitHub 在 2025 年推出開源工具 Spec Kit 的時候，也講了一樣的觀察：AI agent 很常寫出「看起來對、但其實沒抓到意圖」的程式，問題通常不在 AI 寫程式的能力，而是我們給它的指令太模糊。他們的解法是：**先寫規格，再寫程式。**

### 🧪 換你試試

把你自己的點子用**一句話**丟給 AI 兩次（兩個新對話），比較一下：

| 這兩次哪裡不一樣？ | 這是我原本心裡想的嗎？ | 我其實已經偷偷決定、但沒說出口的事 |
| --- | --- | --- |
|  |  |  |

最右邊那一欄，就是你等一下要寫進規格的東西。

## 1. 規格是什麼？給人也給 AI 的施工圖

蓋房子不會直接叫工人開始砌磚，會先有一份施工圖：幾房幾廳、門開哪邊、哪裡要插座。
軟體也一樣。

> **規格（Specification，簡稱 Spec）**：一份描述「要做什麼、為什麼做、怎樣算做好」的文件。

注意，規格寫的是 **What（做什麼）** 和 **Why（為什麼）**，**不寫 How（怎麼做）**。
「用 Python 還是 JavaScript」「資料存在哪裡」這些技術決定，是下一步「計畫」的事。

一個 AI 時代的專案，通常會有這幾份文件：

| 文件 | 給誰看 | 寫什麼 | 誰寫 |
| --- | --- | --- | --- |
| `README.md` | 人（使用者、隊友、未來的你） | 這是什麼、怎麼安裝、怎麼用 | 你（可請 AI 潤飾） |
| `SPEC.md` | 你和 AI | 要做什麼、不做什麼、怎樣算做好 | 你主導，AI 幫忙追問 |
| 計畫（Plan） | 你和 AI | 用什麼技術、分哪些模組、資料怎麼存 | AI 提案，你挑選 |
| 任務（Tasks / Issues） | AI 和你 | 一張一張的小工作單 | AI 拆，你審 |
| `AGENTS.md` / `CLAUDE.md` | AI | 這個專案的工作守則 | 你 |

> **Prompt 用完就丟，規格會留下來。**
> 每次開新對話，AI 都會失憶；但只要規格在專案裡，它隨時可以重新讀一遍，理解跟上次一樣的東西。

<details>
<summary>業界的三種「規格先行」流派（打開看看）</summary>

這幾年 AI coding 工具不約而同地走向同一件事：**先規格、後程式**。名字不同，骨架一樣。

| 工具 | 流程 | 產出的文件 |
| --- | --- | --- |
| GitHub Spec Kit（開源） | Specify → Plan → Tasks → Implement | spec、plan、tasks |
| AWS Kiro | Requirements → Design → Tasks | `requirements.md`、`design.md`、`tasks.md` |
| Claude Code（官方建議） | 先讓 AI 訪問你，把結果寫進 `SPEC.md`；用 Plan 模式先規劃再動手 | `SPEC.md`、`CLAUDE.md` |

GitHub 那篇介紹 Spec Kit 的文章有一句話很值得記：過去我們說「程式碼才是唯一的真相」，現在要變成「**意圖才是唯一的真相**」。
程式碼可以重寫，但「你到底想要什麼」必須被好好保存下來。

另外一個重點：規格是**活的**。做到一半發現新東西，先改規格，再改程式。

</details>

## 2. 一頁規格：七個欄位

不用寫成企劃書。一頁、七個欄位就夠了。

### 2.1 先看範例

```markdown
# 三峽午餐輪盤 SPEC

## 1. 問題
每天中午跟室友花 15 分鐘討論吃什麼，最後還是吃同一家。

## 2. 誰會用
我自己和兩個室友。用手機打開。

## 3. 這次要做的事（核心功能）
- 我可以自己新增、刪除口袋名單裡的店家
- 按一個按鈕，隨機抽出一家
- 最近 3 天吃過的店，不會被抽到

## 4. 這次明確不做（非目標）
- 不做登入、不做多人帳號
- 不串 Google Maps、不自動抓店家
- 不做評分和留言
- 不做 App 上架，用手機瀏覽器打開就好

## 5. 使用流程
打開網頁 → 看到口袋名單 → 按「抽！」→ 顯示今天吃哪家 → 按「就這家」記錄下來

## 6. 需要記住的資料
- 店家：名字、類型（飯／麵／其他）
- 吃飯紀錄：哪一天吃了哪一家

## 7. 驗收條件
（下一節教你寫）
```

是不是比「幫我做一個決定午餐吃什麼的 App」清楚太多了？

### 2.2 每個欄位在幹嘛

| 欄位 | 回答什麼問題 | 常見錯誤 | 改成這樣 |
| --- | --- | --- | --- |
| 1. 問題 | 為什麼要做？ | 「市面上沒有好用的」 | 寫一個具體情境：誰、在什麼時候、遇到什麼麻煩 |
| 2. 誰會用 | 給誰用？在哪用？ | 「所有人」 | 越具體越好，「我和室友、用手機」 |
| 3. 要做的事 | 使用者能做到什麼？ | 寫技術：「用 React 做前端」 | 寫行為：「我可以……」 |
| 4. **不做的事** | 這次刻意不碰什麼？ | 空白 | 至少寫 3 條，越多越好 |
| 5. 使用流程 | 一步一步怎麼用？ | 只寫功能清單 | 用箭頭寫出一條從頭到尾的路 |
| 6. 資料 | 程式要記得什麼？ | 忘了寫 | 想想「關掉再打開，什麼東西要還在？」 |
| 7. 驗收條件 | 怎樣算做好？ | 「要好用」 | 寫成可以檢查對錯的句子（下一節） |

### 2.3 為什麼「不做的事」最重要？

因為 **AI 超級熱心**。
你說要做午餐輪盤，它可能順手幫你加上登入系統、深色模式、多國語言，還有一個你看不懂的資料庫。
每多一個功能，就多一個會壞的地方。

> **非目標（Non-goals）是你給 AI 的煞車。** 沒寫「不做」，AI 就會一直做。

第五課學過的模組責任也用得上：寫「不做的事」的時候，順便想想「這樣就不需要哪個模組」。不做登入 → 不需要帳號模組；不串地圖 → 不需要外部 API。整個專案瞬間瘦一圈。

### 2.4 寫不出來？讓 AI 訪問你

Claude Code 的官方最佳實踐裡有一招很好用：**當你還沒想清楚的時候，不要硬寫，請 AI 反過來訪問你，問到它能寫出規格為止。**

- 參考用 prompt：

```text
我想做：［一句話描述你的點子］。
請你扮演產品經理，先不要寫任何程式。
一次只問我一個問題，問到你能幫我寫出一頁規格為止。
規格要包含：問題、誰會用、要做的事、這次明確不做的事、使用流程、需要記住的資料。
問完之後，整理成 SPEC.md 給我。
```

小技巧：

- AI 問你的問題，如果你回答「都可以」，那就代表**你還沒決定**，請自己決定一個。
- AI 幫你寫好之後，**一定要自己讀一遍**，把不是你要的刪掉。規格是你的，不是 AI 的。

### 🧪 換你寫

開一個 `SPEC.md`，先把七個欄位的前六個寫完。

- 🟢 **入門路線**：用上面的 prompt 讓 AI 訪問你，再自己修改。
- 🔵 **進階路線**：自己先寫，再請 AI 「挑出這份規格裡模糊、會讓工程師猜的地方」。

## 3. 驗收條件：怎樣才算「做好了」

規格裡最容易被跳過、但最有用的就是這一欄。

> **驗收條件（Acceptance Criteria）**：一組可以判斷「對」或「錯」的句子，用來檢查功能有沒有做好。

沒有驗收條件會發生什麼事？

```text
你：功能做好了嗎？
AI：做好了！
你：（打開來看）……按鈕按了沒反應啊。
AI：抱歉！我修好了！
你：（再打開）……現在會抽到昨天吃過的店。
```

你跟 AI 對「做好」的定義不一樣。驗收條件就是把定義先講好。

### 3.1 Given / When / Then：三段式寫法

這個寫法來自「行為驅動開發（BDD）」，柏克萊大學的軟體工程課（CS169）就用它把需求寫成可以檢查的情境。

```text
Given（在什麼情況下）
When （使用者做了什麼）
Then （系統應該怎麼反應）
```

午餐輪盤的例子：

```text
情境 1：正常抽籤
Given 口袋名單裡有 5 家店，最近 3 天都沒吃過
When  我按下「抽！」
Then  畫面顯示其中一家店的名字

情境 2：避開最近吃過的
Given 口袋名單裡有 5 家店，其中「阿婆麵」是昨天吃的
When  我按下「抽！」
Then  抽到的不會是「阿婆麵」

情境 3：名單是空的
Given 口袋名單裡沒有任何店
When  我按下「抽！」
Then  畫面顯示「先新增幾家店吧！」，而不是當掉或一片空白
```

一個情境大概 3–5 句就好，太長代表你一次想測太多東西。

### 3.2 爛驗收 vs 好驗收

| ❌ 爛驗收（沒辦法判斷對錯） | ✅ 好驗收（一看就知道過沒過） |
| --- | --- |
| 介面要好看 | 在手機上打開，不用左右滑就能看到「抽！」按鈕 |
| 要很快 | 按下「抽！」後 1 秒內顯示結果 |
| 要能處理錯誤 | 名單是空的時候按「抽！」，會顯示提示文字 |
| 資料要保存 | 新增一家店後重新整理頁面，那家店還在 |

### 3.3 每個功能至少寫兩條

一條**正常情況**，一條**例外情況**。
第五課我們講過「回饋」：系統做完事要讓使用者知道，**做不到的時候更要讓使用者知道**。例外情境就是在檢查這件事。

<details>
<summary>另一種寫法：EARS（打開看看）</summary>

AWS 的 Kiro 用另一種格式寫需求，叫做 EARS（Easy Approach to Requirements Syntax）。最常用的句型長這樣：

```text
當［某件事發生］時，系統應該［做出某個反應］。
```

例如：

```text
當使用者按下「抽！」且名單為空時，系統應該顯示「先新增幾家店吧！」。
當使用者新增店家時，系統應該把店家存起來，重新整理後仍然存在。
```

跟 Given/When/Then 一樣的精神：**把「應該怎樣」寫成可以檢查的句子**。挑一種你順手的就好。

</details>

<details>
<summary>驗收條件 → 自動測試（打開看看）</summary>

第五課最後我們請 AI 寫過測試腳本。有了驗收條件，你可以直接請 AI 把它們變成自動測試：

```text
請根據 SPEC.md 裡的驗收條件，為每一條寫一個自動測試。
測試名稱請用驗收條件的情境名稱。
先列出你打算寫的測試清單給我確認，不要直接寫。
```

之後每次 AI 改完程式，跑一次測試就知道有沒有把舊功能弄壞。這就是第五課講的「回歸測試」。

</details>

### 🧪 換你寫

把你 `SPEC.md` 的第 7 欄補上：每個核心功能各寫 **1 條正常 + 1 條例外**。

## 4. 從規格到計畫到任務

規格寫好了，可以叫 AI 開工了嗎？
還不行。**先讓 AI 想，不准它寫。**

```text
SPEC（做什麼） → PLAN（怎麼做） → TASKS（拆成小工作） → 一次做一個
```

### 4.1 計畫：讓 AI 提方案，你來挑

- 參考用 prompt：

```text
請讀 SPEC.md。先不要寫任何程式。
請提出兩種做法，用表格比較：
1. 用什麼工具／語言；
2. 會分成哪些模組，各負責什麼（介面／規則／資料／回饋）；
3. 資料存在哪裡；
4. 對新手來說的難度、需要安裝什麼；
5. 有沒有哪一條規格會因此做不到。
最後推薦一個，並說明理由。
```

為什麼要兩種？因為只有一種方案的時候，你沒辦法判斷它好不好。
有比較，你才有選擇權。

看計畫時問自己：

| 檢查點 | 為什麼重要 |
| --- | --- |
| 有沒有出現我規格裡「不做」的東西？ | AI 很愛偷渡功能 |
| 要裝的東西我裝得起來嗎？ | 環境設定是新手最常卡關的地方 |
| 模組切分我看得懂嗎？ | 看不懂的架構，壞了你也修不了 |
| 資料存哪裡？關掉再開還在嗎？ | 對應規格第 6 欄 |

### 4.2 任務：小到可以單獨完成、單獨檢查

- 參考用 prompt：

```text
我選擇方案［A／B］。請根據 SPEC.md 和這個方案，把工作拆成任務清單：
- 每個任務要能單獨完成，而且做完可以用驗收條件檢查；
- 第一個任務必須是「能跑起來的最小版本」；
- 標出任務的先後順序；
- 不要加入 SPEC.md 沒有的功能。
```

拿到清單後，**你的工作是刪**。

```text
□ 有沒有任務對應不到規格？→ 刪掉
□ 有沒有任務大到一次對話做不完？→ 請 AI 再拆
□ 第一個任務做完，我能不能打開來看到東西？→ 不能就重排
```

> **AI 負責生成，你負責確認。** 規格、計畫、任務，每一步都要你點頭才往下走。

## 5. 搬進 GitHub：README、SPEC、Issue

規格和任務不要只留在聊天紀錄裡。聊天紀錄會被洗掉，**專案資料夾不會**。

### 5.1 用網頁版開一個 repo（不用打指令）

```text
1. 登入 GitHub → 右上角「+」→ New repository
2. Repository name：取個英文名字，例如 lunch-roulette
3. 勾選「Add a README file」
4. 按 Create repository
5. 在 repo 頁面按「Add file」→「Create new file」
6. 檔名打 SPEC.md，把你的規格貼進去 → Commit changes
```

完成！你的施工圖現在有版本紀錄了。

### 5.2 README 寫什麼？

README 是給**人**看的。最少寫這四件事：

```markdown
# 三峽午餐輪盤
幫我和室友在 3 秒內決定午餐吃什麼的小工具。

## 怎麼用
（之後補：打開網址／執行指令）

## 目前進度
- [x] 規格完成（見 SPEC.md）
- [ ] 第一版可以抽籤

## 這次不做
登入、地圖、評分。
```

### 5.3 把任務變成 Issue

Issue 就是 GitHub 上的「工作單」。一個任務開一張。

```text
repo 頁面上方 → Issues → New issue
```

Issue 模板：

```markdown
標題：[任務 1] 顯示口袋名單並可以新增店家

## 要做什麼
在畫面上顯示口袋名單，並可以輸入店名新增。

## 驗收條件（從 SPEC.md 複製）
- Given 名單是空的 When 我輸入「阿婆麵」並按新增 Then 名單出現「阿婆麵」
- Given 我新增了一家店 When 我重新整理頁面 Then 那家店還在

## 這張不做
抽籤功能（任務 2 再做）。
```

注意最後一行：**每張 Issue 也有自己的「不做」**。這樣 AI 就不會在做任務 1 的時候，順便把任務 2、3、4 全寫了（然後全部壞掉）。

<details>
<summary>🔵 進階：AGENTS.md / CLAUDE.md，AI 的工作守則（打開看看）</summary>

README 是給人的說明書，那給 AI 的呢？
現在很多 AI coding 工具會自動讀專案裡的一個特定檔案：

| 檔名 | 誰會讀 |
| --- | --- |
| `AGENTS.md` | 一個開放格式，Codex、Cursor、Gemini CLI、GitHub Copilot 等很多工具都支援 |
| `CLAUDE.md` | Claude Code |

範例：

```markdown
# 給 AI 的工作守則

## 這個專案
三峽午餐輪盤。規格在 SPEC.md，動工前一定要先讀。

## 怎麼執行
用瀏覽器打開 index.html。

## 規則
- 一次只處理一個 Issue。
- 修改前先列出計畫，等我確認。
- 不要新增 SPEC.md 沒有的功能。
- 要安裝新套件之前先問我。
```

重點是**短**。Claude Code 的官方文件特別提醒：這個檔案每次對話都會被讀進去，所以只寫 AI 從程式碼裡看不出來的東西就好。寫太長，重要的規則反而會被淹沒。

</details>

<details>
<summary>🔵 進階：用 GitHub Projects 看板管理進度（打開看看）</summary>

Issue 多起來之後，可以開一個看板：

```text
repo 上方 → Projects → New project → 選 Board 模板
```

預設會有三欄：`Todo`、`In Progress`、`Done`。把 Issue 拖進去，一眼就知道做到哪。

給自己一個規則：**In Progress 那一欄永遠只放一張。**
同時開工好幾張，是 side project 做不完最常見的原因之一。

想排時程的話，可以在 Issues → Milestones 建立里程碑（例如「第一版：能抽籤」），把相關 Issue 掛上去。

</details>

## 6. 開工：一次只給 AI 一個 Issue

終於可以叫 AI 寫程式了！流程是這樣：

```text
開新對話 → 給 SPEC + 一張 Issue → AI 先列計畫 → 你確認 → AI 實作
→ 用驗收條件檢查 → git commit → 關掉 Issue → 下一張
```

是不是很眼熟？這就是第五課的工作流，只是現在多了「規格」當地圖：

```text
Understand → Locate → Plan → Ask AI → Review → Test → Debug
   ↑ SPEC.md      ↑ PLAN       ↑ Issue           ↑ 驗收條件
```

- 參考用 prompt：

```text
請先讀 SPEC.md。
我們現在只做這張 Issue：［貼上 Issue 內容］。
1. 先列出你要新增或修改哪些檔案、各做什麼，等我確認再動手；
2. 只做這張 Issue，不要做其他任務；
3. 做完後，逐條說明每個驗收條件要怎麼檢查。
```

### 6.1 AI 跑偏了怎麼辦？

| 狀況 | 怎麼做 |
| --- | --- |
| AI 開始改你沒叫它改的檔案 | 馬上喊停，提醒它「只做這張 Issue」 |
| 同一個問題修了兩次還是錯 | **不要修第三次**。開新對話，把剛剛學到的寫進更好的 prompt |
| 做的過程發現規格沒想到的事 | 先停下來改 `SPEC.md`，再繼續 |
| 驗收條件全過，但你覺得怪怪的 | 代表驗收條件寫得不夠，補一條再修 |

第二條是 Claude Code 官方文件的建議：同一件事糾正兩次還錯，對話裡已經堆了兩次失敗的嘗試，AI 會一直被它們干擾。重新開始，通常比硬修更快。

### 6.2 做完記得存檔

第五課教過的 git 指令派上用場了：

```shell
git add .
git commit -m "完成任務 1：顯示並新增口袋名單"
```

如果你是用 GitHub 網頁版或 AI 工具內建的版本控制也可以，重點是：**每完成一張 Issue，就存一個版本**。這樣 AI 下一張改壞了，你隨時可以退回來。

## 7. 大挑戰時間

選一個等級挑戰：

- **Level 1**：完成 `SPEC.md` 七個欄位，至少 2 個功能各有 2 條驗收條件。
- **Level 2**：在 GitHub 開 repo，放好 README 和 SPEC，開出至少 3 張 Issue。
- **Level 3**：讓 AI 完成第一張 Issue，逐條通過驗收條件，並 commit。
- **Level 4（🔵 進階）**：用 GitHub Spec Kit（`specify init`）或 Kiro 跑一次完整的規格流程，比較它產出的文件和你手寫的差在哪。

### 完成前的自我檢查表

| 檢查項目 | 有沒有？ |
| --- | --- |
| 規格裡有「這次明確不做」，而且至少 3 條 |  |
| 每條驗收條件都能判斷對錯 |  |
| 每張 Issue 都有自己的驗收條件和「這張不做」 |  |
| 第一張 Issue 做完就能打開來看到東西 |  |
| 我能不看 AI，用自己的話講出這個專案要做什麼 |  |

最後一條最重要。如果你講不出來，代表規格還是 AI 的，不是你的。

## 大總結啦

> **「寫程式交給 AI，但『要寫什麼』永遠是你決定的。」**

### 一：規格三件套

1. **SPEC.md**：要做什麼、**不做什麼**、怎樣算做好。寫 What 和 Why，不寫 How。
2. **驗收條件**：Given / When / Then。每個功能至少一條正常、一條例外。
3. **Issue**：一次給 AI 一張，每張都有自己的驗收條件和「這張不做」。

### 二：規格先行的四步

$$\text{Specify} \rightarrow \text{Plan} \rightarrow \text{Tasks} \rightarrow \text{Implement}$$

* **Specify（規格）**：讓 AI 訪問你，但規格是你的。
* **Plan（計畫）**：讓 AI 提兩個方案，你來挑。
* **Tasks（任務）**：讓 AI 拆，你來刪。
* **Implement（實作）**：一次一張，做完驗收、commit、下一張。

### 三：給 AI 的三個煞車

* **非目標**：沒寫「不做」，AI 就會一直做。
* **一次一張 Issue**：不讓 AI 一口氣把整個專案寫完（然後全壞）。
* **先計畫再動手**：每一步都等你點頭。
