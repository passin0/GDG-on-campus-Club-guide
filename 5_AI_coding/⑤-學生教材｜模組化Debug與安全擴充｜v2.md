# 第 ⑤ 堂｜從 Vibe Coding 到 AI Coding：模組化 Debug 與安全擴充

> AI 幫你寫出一個 App 之後，真正困難的事情才開始：  
> 壞掉時去哪找？想加功能時，怎麼不弄壞其他地方？

## 今天要完成什麼？

你會以一個小型「活動報名工具」為例，完成一次受控改動。下課時，你應該留下：

1. 一張模組責任地圖；
2. 一份可重現的 Debug 紀錄；
3. 一項新功能的最小修改與驗收結果。

今天不要求你背語法，也不要求從零寫完 App。重點是：**你能指揮 AI 改對地方，並確認它沒有順便弄壞別的地方。**

---

## 1. 一個功能不是一段 Code

想像報名工具有這個需求：

> 活動額滿時，不能再新增一般報名；使用者應看見「額滿」提示。

它不是只多一個 `if`。一個功能通常有這些部分：

```text
使用者輸入／按下按鈕
        ↓
介面：收集資料、顯示畫面
        ↓
規則：可不可以報名？是否重複？
        ↓
資料／狀態：目前名額、已報名者是誰？
        ↓
回饋：成功、額滿、重複報名時怎麼說？
```

如果 AI 生成的程式把全部塞在同一段，短期能跑，之後卻很難找問題。模組化的目的不是炫技，而是替每一類工作貼上清楚的地址。

## 2. 模組化：每一區只負責一件主要的事

| 模組 | 負責什麼？ | 不應負責什麼？ |
| --- | --- | --- |
| `報名介面` | 收集姓名、讓人按下報名 | 決定名額是否足夠 |
| `報名規則` | 判斷額滿、重複、資料是否完整 | 直接排版畫面 |
| `報名資料` | 讀取／新增報名紀錄、記住名額 | 決定提示文字 |
| `回饋顯示` | 告訴使用者成功或失敗原因 | 修改報名資料 |

一個模組不一定等於一個檔案；先看它的**責任**。之後你才會用資料夾、檔案與 Function 去找它。

### 練習 ①：模組責任卡

請挑一個你做過或正在看的功能。

| 模組／區塊 | 它該負責什麼？ | 它會拿到什麼？ | 它交出什麼？ | 它不該處理什麼？ |
| --- | --- | --- | --- | --- |
|  |  |  |  |  |
|  |  |  |  |  |
|  |  |  |  |  |

> Function 是模組裡的一個小動作。讀 Function 時，先問：它屬於哪個責任區？拿到什麼？改變或回傳什麼？

## 3. Debug 不是亂搜，是縮小範圍

情境：名額明明已滿，使用者卻還能報名成功。

先不要叫 AI「幫我修」。走下面的漏斗：

```text
重現問題
→ 分類問題
→ 找負責模組
→ 檢查它的輸入、輸出與規則
→ 最小修改
→ 回歸測試
```

### 3.1 重現與分類

| 我觀察到的現象 | 比較可能是哪一類？ |
| --- | --- |
| 按鈕按了完全沒反應 | 介面／事件 |
| 名額明明是 0，畫面卻說還能報 | 資料／狀態 |
| 資料正確，但仍然允許超額 | 規則 |
| 已擋下報名，但沒有告訴使用者原因 | 回饋顯示 |

### 給 AI 的 Debug Prompt

```text
這個功能的責任分成：［列出你的模組］。
我做了［操作］，原本預期［結果］，實際卻［結果］。
我懷疑問題在［模組］，因為［理由］。

請不要重寫整個專案。請：
1. 先確認我的問題分類是否合理；
2. 指出應檢查的 Function、資料或規則；
3. 提出最小修改方案；
4. 說明這個修改可能影響哪些舊功能。
```

## 4. 安全擴充：先寫規則，再請 AI 寫 Code

現在加入一項功能：**額滿後可加入候補名單。**

不要直接說「幫我加候補」。先說清楚功能契約。

| 問題 | 候補功能的答案示例 |
| --- | --- |
| 誰在什麼情況下使用？ | 活動額滿後，想參加的學生 |
| 系統要記得什麼？ | 候補者、加入時間、順序 |
| 新規則是什麼？ | 額滿才可候補；同一人不能重複加入 |
| 使用者看見什麼？ | 「已加入候補，第 3 位」 |
| 這次不做什麼？ | 自動通知、候補自動轉正、付款 |

我要新增／修改：＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿

使用者觸發它的方式：＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿

系統需要記得：＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿

新規則與例外：＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿

這次明確不做：＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿

## 5. 先保留退路，再做最小改動

在讓 AI 修改之前：

1. 保留可運作版本：截圖、複製專案或建立版本紀錄。
2. 要求 AI 先列「會改哪些區塊、為什麼」，不要立刻貼完整新專案。
3. 要求最小修改：新規則應放進誰的責任區？
4. 修改後，同時驗證新功能與原本功能。

### 給 AI 的擴充 Prompt

```text
我要加入這項功能：［貼上功能變更卡］。
目前模組責任是：［貼上模組責任卡］。

請先不要直接改程式。請列出：
1. 需要修改或新增的模組；
2. 每個模組的最小改動；
3. 哪些舊功能可能受影響；
4. 建議的驗收案例。

等我確認範圍後，再只實作這些最小改動。
```

## 今天帶走的工作流

```text
看見行為
→ 用模組責任縮小問題
→ 描述可重現的證據
→ 先定規則與範圍
→ 讓 AI 提出最小修改
→ 驗證新功能，也驗證舊功能
```

下一堂課，我們會把這個「一個功能的模組地圖」擴大，變成一個從想法到可開工專案的計畫。
