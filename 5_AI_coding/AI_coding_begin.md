## Vibe coding 跟 AI coding 差在哪？

在現在業界或許你們會有一些人覺得 AI 要取代軟體工程師了，但是你們這些手上有 AI 的同學們，用的工具都差不多，還沒成為工程師呢。所以 Vibe coding 跟 AI coding 差在哪？真正的 AI coding 需要會什麼？常見的說法有這些：

- 系統架構設計與抽象化能力
- Context 管理與 Token 預算編排
- 程式碼審查與除錯
- 軟體安全與合規
- 自動化測試開發規劃
- 效能瓶頸診斷與優化
- 併發與非同步編程模型
- AI Agent 異步鏈接與開發工具整合

「聽起來很複雜？其實說白了只有一件事：你從『打字工人』變成了『專案監工』。監工不用親自蓋牆，但必須看得懂藍圖、知道哪間房間漏水該找誰修。」\
「至少不會是，我家漏水了，水電工ChatGPT，我不告訴你我家地址，幫我修好我家壞掉的某個地方。」
所以只要你知道如何善用軟體工程的常識、跟指揮你的 AI，那你距離 AI 開發者不遠了。

## 0. AI 都會寫 Code 了，為什麼還要學？｜5 分鐘

如果 AI 幫你寫了 500 行 Code，你敢直接放進專案嗎？ \
如果專案在某次修改後發生錯誤，你要如何讓 AI 去修改？\
如果你想給你的程式增加一個新功能，你要如何指揮 AI？

先想四件事：它在哪裡？它在做什麼？壞掉時該找誰？AI 改了 A，為什麼 B 可能一起壞？

> **Generate ≠ Correct。** AI 是很快的實作者，但你仍是決定範圍、檢查結果的人。

## 1. 最低限度的 Code 閱讀能力｜10 分鐘

今天的第一節，你要認識貫串整個程式碼的概念  **Function ( 函式 )**  
不用看懂每一行，但是你要會疊積木。

先看一段 Python 語言的 Function：

```python
def calculate_total(price, quantity): # 名稱(輸入,輸入)
    output = price * quantity # 處理
    return output # 輸出
```

不必先學 Python。只要看到：

```text
名稱：calculate_total
輸入：price、quantity
處理：把兩者相乘
輸出：總金額
```

讀 Function 的第一步：**先看它吃什麼、吐什麼，再決定要不要看裡面。** 
```text
輸入 ---> 函式做事 ---> 輸出
```
| 名稱 | 它需要什麼？ | 它完成／回傳什麼？ | 我還不確定什麼？ | 

函式的名稱就是它的功能，只要取名得好，你需要的是英文好，不是看懂程式碼。然後你就可以逐漸知道程式在幹嘛。
```python
import discord
from discord.ext import commands

intents = discord.Intents.default()
intents.message_content = True
bot = commands.Bot(command_prefix='!', intents=intents)

@bot.command()
async def hello(ctx):
    await ctx.send(f'你好，{ctx.author.name}！')

bot.run('YOUR_BOT_TOKEN_HERE')
```

## 2. 為什麼 Code 要拆開？｜12 分鐘

就如同專案管理需要 WBS（Work Breakdown Structure，工作分解結構）\
![wbs範例](https://hackmd.io/_uploads/BygDLN4tMx.png)

雖然 AI 很方便，但是如果把所有程式碼給他，很燒 token 以外也容易出現幻覺。所以我們寫軟體也需要分工，寫清楚誰負責什麼，第一個當然就是分工寫好要互相丟包很方便，第二個就是對我們來說，這些知識能夠用來指揮 AI 去找到問題跟 debug。
```text
我想要做一個 Youtube
---> 1. 拆分功能模組：首頁、影片區、留言區、個人帳號登入、個人化設定
---> 2. 影片區還可以拆分：下載影片、加載一個小時的廣告、影片快轉
---> 3. 影片下載還可以繼續拆：檢查影片存取、檢查網路連結、精彩時刻標籤資料
```
### 我們來細講
先來看個例子
這兩種專案，你想在哪一種裡面找「登入壞掉」的問題？

```text
app.py
└── 800 行全部混在一起
```

```text
app.py        # 啟動與路由
user.py       # 使用者相關規則
database.py   # 讀寫資料
email.py      # 寄信
```
或許一眼就看的出來哪一個比較整齊、比較好找，那這些東西就可以看到下面的大重點。

### Module（模組）：把複雜事情切成可分開理解、各有主要責任的部分。

| 模組 | 主要責任 | 不該順便負責 |
| --- | --- | --- |
| 介面 | 接收操作、顯示結果 | 決定商業規則 |
| 規則 | 判斷允許、拒絕與例外 | 排版畫面 |
| 資料 | 保存、讀取、更新資料 | 寫提示文案 |
| 回饋 | 顯示成功或失敗原因 | 偷改資料 |

### Interface (介面)：你不必知道所有內部細節

```python
send_email(to, subject, content)
```

大部分的函式就是做好的積木，你只要會挑選，然後把它疊起來。
你知道「給它收件人、標題、內容，它會寄信」就能使用它。SMTP、網路重試、認證等細節可以先不懂。

> 看懂軟體，不等於看懂每一行 Code；而是知道每一塊負責什麼、如何和其他部分溝通。


### Data & State（資料與狀態）：程式現在到底記得什麼？

```text
Data：程式需要記住、查詢、保存的內容，可能會透過資料庫儲存
State：程式現在正在處理的情況，可能關掉或是刷新就消失了
```


一個 App 不會每次按按鈕都失憶。
它需要記得很多東西。
例如 Todo App：

```text
有哪些 Todo？
哪一個已經完成？
誰建立的？
建立時間是什麼？
```

這些叫做：

> **Data（資料）**

但是程式除了保存長期資料之外，也有一些「現在這一刻」的狀況。

```text
使用者現在正在輸入什麼？
目前有沒有正在讀取資料？
畫面現在顯示全部 Todo 還是已完成 Todo？
錯誤訊息要不要顯示？
```

這些通常叫做：

> **State（狀態）**


如果你遇到：
> 「我明明新增成功了，但畫面沒有更新。」
> 「我重新整理之後，剛剛新增的東西全部不見。」

你可以找看看：

```text
資料有沒有真的新增？
畫面讀到的是不是最新資料？
現在改到的是 State，還是真的有存成 Data？
```

很多看起來像畫面壞掉的問題，其實不是 UI 壞掉，而是：

> **資料跟畫面沒有同步，在某個資料狀態環節上出問題了。**

---

### Rules / Business Logic（規則／商業邏輯）：系統到底允許你做什麼？

介面讓使用者操作。
資料讓系統記得事情。

但是「這件事情可不可以做」，需要由規則決定。\
而這些規則，AI不一定能完全知道你的想法，需要你主動給出建議。

例如 記事本 Todo App 看起來很簡單，但其實可能也有規則：

```text
- 空白 Todo 不能新增
- Todo 名稱不能超過 100 個字
- 同一件 Todo 不要一直重複新增
- 已完成 Todo 才能刪除
```

如果是活動報名系統，規則可能是：

```text
- 名額滿了不能報名
- 同一個人不能重複報名
- 超過截止時間不能送出
- 管理員才能編輯活動資訊
```

如果你遇到：

> 「明明活動額滿了，系統還是讓我報名。」

你可以開始往這裡找：

```text
名額資料是不是正確？
檢查名額的規則有沒有被呼叫？
判斷條件是不是寫反了？
```
這比直接對 AI 說：
```text
活動報名怪怪的，幫我修。
```
有用太多了。

> **把人類世界的需求，翻譯成系統可以判斷的條件，這就是規則。**

這就是我們在講的 Rules（規則）或 Business Logic（商業邏輯）。如果你嘗試寫一個軟體介紹書給一般人看，你不需要寫你用了什麼很酷的技術，重點是你放在其中的邏輯要讓一般人理解。

這點如果各位有興趣去黑客松或是商業競賽時跟別人介紹中很重要喔。

---
### Feedback（回饋）：系統做完事情，有沒有跟使用者講？

程式內部成功，不代表使用者知道成功。
例如使用者按下報名。
系統可能真的已經把資料存好了。
但是如果畫面什麼都沒顯示，使用者可能會：

```text
蛤？有成功嗎？
再按一次好了。
```

然後：

```text
重複報名，瘋狂按按鍵，你就會收到 100 張一樣的表單。
```

所以軟體需要 Feedback（回饋）。

```text
使用者按下新增 > 系統檢查規則 > 資料新增成功 > 畫面顯示：已新增 Todo
```

一個好的回饋，至少要回答三件事：

```text
我剛剛的操作成功了嗎？
如果失敗，原因是什麼？
我接下來可以做什麼？
```

下次遇到問題，你可以往這裡找：

```text
成功或失敗的結果有沒有傳回畫面？
畫面有沒有真的顯示訊息？
錯誤訊息有沒有講人話？
```

【 **一個系統不只是要做對事情，還要讓使用者跟開發者知道它做對了** 】

## 4. 連心湖天鵝都該知道 AI Coding 的工作流｜8 分鐘

不要這樣做：

```text
想功能 → 叫 AI 寫 → 祈禱 → 你寫錯了！爛 AI！
```

請走這一輪：

```text
Understand → Locate → Plan → Ask AI → Review → Test → Debug
```

| 步驟 | 問自己什麼？ |
| --- | --- |
| Understand | 我要的行為與規則是什麼？ |
| Locate | 目前功能在哪個模組？ |
| Plan | 最小改動會影響哪些部分？ |
| Ask AI | 我怎麼限制它的任務？ |
| Review | 它實際改了什麼？ |
| Test | 新規則有成立嗎？舊功能還好嗎？ |
| Debug | 問題在哪一個責任區？ |

#### P.S.以上這些每一步都可以跟 AI 討論，但是建議至少給一個系統設計的摘要文件(也可以用 AI 生成沒錯)，減少讓 AI 一直吃一整個專案程式碼的問題。

## 5. 大挑戰時間：擴充既有 App｜30 分鐘

你可以選一個難度：

- Level 1：新增一個欄位或顯示資訊。
- Level 2：新增一條規則，例如空白 Todo 不可新增。
- Level 3：自訂一項功能，但必須先說明可能影響哪些模組。

### 5.1 先嘗試寫下功能變更草稿

我要新增／修改：＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿

使用者怎麼觸發：＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿

新規則與例外：＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿

可能影響的模組：＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿

這次明確不做：＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿

### 5.2 先讓 AI 規劃，不准直接修改

- 參考用 prompt：
```text
作為一個 [使用者角色]，我希望能 [觸發動作]，以便於 [達到什麼價值/目的]。
我要加入這項功能：［功能變更稿］。
目前我理解的模組責任是：［模組地圖］。

請先不要修改程式。請列出：
1. 需要修改或新增的模組與理由；
2. 每個模組的最小改動；
3. 可能影響的既有功能；
4. 建議的驗收方式
5. 系統應該 [提示錯誤] 而不是崩潰
```

### 5.3 修改前保留退路，備份很重要

複製專案或建立版本紀錄(git)。確認 AI 的計畫後，才要求它依計畫做**最小修改**。修改後，看它改了哪些區塊；若它重寫整個專案，先停下來問原因。

### 5.4 驗收與回歸測試

| 測試案例 | 預期結果 | 實際結果 | 通過？ |
| --- | --- | --- | --- |
| 新功能的一般情況 |  |  |  |
| 新功能的一個例外 |  |  |  |
| 原本功能仍可使用 |  |  |  | 

一般工程師會針對重要的功能設計一個測試，模擬輸入並寫下預期輸出最後檢測，也是現代 AI coding 人重要的檢查工作。

## 6. Debug：錯誤訊息是診斷資訊｜10 分鐘

看到錯誤時，先重現，再分類：

| 現象 | 優先檢查 |
| --- | --- |
| 按鈕沒反應 | 介面／事件 |
| 畫面資料不對 | 資料／狀態 |
| 資料正確卻允許不該做的事 | 規則 |
| 成功或失敗沒有正確顯示 | 回饋 |

一片紅字，先不要急，做兩件事，重新運作嘗試讓 bug 再次出現，第二個複製錯誤的訊息後，來跟 AI 一起分析哪裡錯了。

- 參考用 prompt：
```text
我做了［操作］；預期［結果］；實際［結果／錯誤訊息］。
我懷疑問題在［模組］，因為［理由］。
請先解釋可能原因與應檢查的位置，不要直接修改。
```
大部分錯誤能歸類成我們一開始提到的四大模組責任區：介面、規則、資料、回饋。
確認原因後，再請 AI 提出最小修正，考慮一下是否可能更動，沿用上面的修改規畫的流程，並重跑剛才的測試。
總結起來就是

```text
Understand → Locate → Plan → Ask AI → Review → Test → Debug → version control → repeat
```
跟上面的差不多吧！

### 一：看懂藍圖的大積木小積木

1. **Function（函式）：** 不要陷入語法細節，先看它**吃什麼（輸入）、吐什麼（輸出）**。名稱寫得好，英文好就能看懂八成。
2. **Module（模組）：** 把大任務拆成獨立負責的小模組（介面、規則、資料、回饋）並且認識以下四個。
- **Interface（介面）：** 了解模組如何溝通，**不必知道裡面的細節也能使用它**。
- **Data & State（資料與狀態）：** 了解程式記得什麼、忘了什麼，並且知道資料與狀態的差別。
- **Rules / Business Logic（規則／商業邏輯）：** 了解系統允許什麼、不允許什麼，並且知道規則與畫面、資料的差別。
- **Feedback（回饋）：** 了解系統做完事情，有沒有跟使用者講，並且知道回饋與畫面、資料、規則的差別。

---

### 二：不用燒香拜拜甩鞭子的（Prompt & Pray）的黃金 7 步工作流

遇到需求或 BUG 時，永遠照這個順序走，**先要求 AI 提出計畫，不要直接重寫**：

$$\text{Understand} \rightarrow \text{Locate} \rightarrow \text{Plan} \rightarrow \text{Ask AI} \rightarrow \text{Review} \rightarrow \text{Test} \rightarrow \text{Debug}$$

* **Understand（理解）：** 弄清商業邏輯與規則。
* **Locate（定位）：** 猜猜看功能或問題在哪個模組。
* **Plan（規劃）：** 讓 AI 提出最小修改方案。
* **Ask AI（指揮）：** 給予明確限制，只修改必要區域。
* **Review（審查）：** 檢查 AI 到底改了什麼，是不是重寫了不該改的地方。
* **Test（測試）：** 驗證新功能成立，且舊功能沒出事（回歸測試）。
* **Debug（除錯）：** 錯誤訊息是診斷報告，先分類責任區再請 AI 修正。

---

### 監工守則：`Generate ≠ Correct`

* **AI 是速度極快但偶爾會幻覺的實作者**，你才是決定範疇（Scope）與驗收品質的人。

* **給 AI 專案時：** 盡量給系統設計摘要（Architecture Summary），不要一次把整個幾萬行的專案丟給它，燒 Token 又容易出錯。

* **AI 一次知道得越多就會越笨**

### 給文組同學的話

身為文組學生，**邏輯表達、人性化需求理解與文字分析**是你們最大的優勢！
軟體開發最難的往往不是「怎麼寫、怎麼讀」，而是「要把需求拆解得多清楚」。只要學會指揮 AI、懂得了模組責任，你不需要成為資工系專家，也能獨立打造出實用的軟體應用，在更多的未來，也許也能整理好自己的想法去跟其他工程師合作。

對資工系或是愛寫程式的同學們來說，時代也有些變了，純手工藝確實不常見了，有時間練習不要失傳了我們手刻 C 語言的功夫。但是但是如果是跟我一樣大學開始寫程式而且真正喜歡打造作品的同學，這些都是軟體工程的基本功，也是未來管理自己與別人的第一步，也可以套用在跨領域的交流上。如果你對這些有興趣，第一張新手藏寶圖給你了，去學習更廣闊的海洋吧，沒事的時候也可以跟我聊聊好玩的想法，說不定能讓我這個學一半就開始寫教材的菜鳥學到很多好東西。
