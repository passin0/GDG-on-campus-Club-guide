# 第 ⑤ 堂｜AI Coding：我可以讓 AI 幫我做軟體，而且開始看得懂它

> AI 讓寫 Code 變快；理解、判斷、驗證反而變得更重要。

## 今天的任務

你會拿到一個已能執行的小專案，完成一次「先理解、再定位、規劃後修改、最後驗證」的改動。下課時你不必背完語法，但應能：

- 說出一個 Function 吃什麼、做什麼、交出什麼；
- 用模組責任找到功能大概在哪；
- 要求 AI 先提出計畫，而不是直接重寫；
- 用測試確認新功能與舊功能都沒有出事。

---

## 0. AI 都會寫 Code 了，為什麼還要學？｜5 分鐘

如果 AI 幫你寫了 500 行 Code，你敢直接放進專案嗎？

請先想四件事：它在哪裡？它在做什麼？壞掉時該找誰？AI 改了 A，為什麼 B 可能一起壞？

> **Generate ≠ Correct。** AI 是很快的實作者，但你仍是決定範圍、檢查結果的人。

---

## 1. 最低限度的 Code 閱讀能力｜10 分鐘

先看一段 Function：

```python
def calculate_total(price, quantity):
    return price * quantity
```

不必先學 Python。只回答：

```text
輸入：price、quantity
處理：把兩者相乘
輸出：總金額
```

讀 Function 的第一招：**先看它吃什麼、吐什麼，再決定要不要看裡面。**

| 名稱 | 它需要什麼？ | 它完成／回傳什麼？ | 我還不確定什麼？ |
| --- | --- | --- | --- |

## 2. 為什麼 Code 要拆開？｜12 分鐘

這兩種專案，你想在哪一種找「登入壞掉」的問題？

```text
app.py
└── 800 行全部混在一起
```

```text
app.py        # 啟動與路由
user.py       # 使用者相關規則
database.py   # 讀寫資料
email.py      # 寄信
```

**Module（模組）**是把複雜事情切成可分開理解、各有主要責任的部分。

| 模組 | 主要責任 | 不該順便負責 |
| --- | --- | --- |
| 介面 | 接收操作、顯示結果 | 決定商業規則 |
| 規則 | 判斷允許、拒絕與例外 | 排版畫面 |
| 資料 | 保存、讀取、更新資料 | 寫提示文案 |
| 回饋 | 顯示成功或失敗原因 | 偷改資料 |

### Interface：你不必知道所有內部細節

```python
send_email(to, subject, content)
```

你知道「給它收件人、標題、內容，它會寄信」就能使用它。SMTP、網路重試、認證等細節可以先不懂。

> 看懂軟體，不等於看懂每一行 Code；而是知道每一塊負責什麼、如何和其他部分溝通。

## 3. 先讀 AI 寫的專案，不急著改｜10 分鐘

本堂範例專案：

```text
todo-app/
├── app.py
├── todo.py
├── database.py
└── README.md
```

先猜：新增一件 Todo 可能在哪裡？資料可能在哪裡？再請 AI 幫你確認。

```text
請不要修改程式。請依 README 與檔案結構，整理：
1. 每個模組的主要責任；
2. 新增 Todo 可能會經過哪些模組；
3. 每個判斷中哪些是事實、哪些只是猜測。
```

| 線索（檔案／Function） | 我猜它負責什麼？ | AI 說什麼？ | 我用什麼證據確認？ |
| --- | --- | --- | --- |
|  |  |  |  |

## 4. AI Coding 的工作流｜8 分鐘

不要這樣做：

```text
想功能 → 叫 AI 寫 → 祈禱
```

請走這一輪：

```text
Understand → Locate → Plan → Ask AI → Review → Test → Debug
```

| 步驟 | 問自己什麼？ |
| --- | --- |
| Understand | 我要的行為與規則是什麼？ |
| Locate | 目前功能在哪個模組？ |
| Plan | 最小改動會影響哪些部分？ |
| Ask AI | 我怎麼限制它的任務？ |
| Review | 它實際改了什麼？ |
| Test | 新規則有成立嗎？舊功能還好嗎？ |
| Debug | 問題在哪一個責任區？ |

## 5. 實作：擴充既有 App｜30 分鐘

你可以選一個難度：

- Level 1：新增一個欄位或顯示資訊。
- Level 2：新增一條規則，例如空白 Todo 不可新增。
- Level 3：自訂一項功能，但必須先說明可能影響哪些模組。

### 5.1 先寫功能變更卡

我要新增／修改：＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿

使用者怎麼觸發：＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿

新規則與例外：＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿

可能影響的模組：＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿

這次明確不做：＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿

### 5.2 先讓 AI 規劃，不准直接修改

```text
我要加入這項功能：［功能變更卡］。
目前我理解的模組責任是：［模組地圖］。

請先不要修改程式。請列出：
1. 需要修改或新增的模組與理由；
2. 每個模組的最小改動；
3. 可能影響的既有功能；
4. 建議的驗收案例。
```

### 5.3 修改前保留退路

截圖、複製專案或建立版本紀錄。確認 AI 的計畫後，才要求它依計畫做**最小修改**。修改後，看它改了哪些區塊；若它重寫整個專案，先停下來問原因。

## 6. Debug：錯誤訊息是診斷資訊｜10 分鐘

看到錯誤時，先重現，再分類：

| 現象 | 優先檢查 |
| --- | --- |
| 按鈕沒反應 | 介面／事件 |
| 畫面資料不對 | 資料／狀態 |
| 資料正確卻允許不該做的事 | 規則 |
| 成功或失敗沒有正確顯示 | 回饋 |

```text
我做了［操作］；預期［結果］；實際［結果／錯誤訊息］。
我懷疑問題在［模組］，因為［理由］。
請先解釋可能原因與應檢查的位置，不要直接修改。
```

確認原因後，再請 AI 提出最小修正，並重跑剛才的測試。

## 收尾｜5 分鐘

你今天學的不是 Function、Module、Interface 的名詞考試，而是：

```text
我知道功能大概在哪。
我能要求 AI 先解釋、再計畫、最後修改。
我會 Review 與 Test，而不是相信「已完成」。
```

下一堂課，你會從自己的想法出發，把它拆成真正可以開工的專案。
